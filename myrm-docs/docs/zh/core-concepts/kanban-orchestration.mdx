# 看板与子 Agent 编排

Myrm 提供可视化看板跟踪复杂多步任务，以及强大的子 Agent 系统（7 种编排模式）。

## 看板任务板

看板提供拖放界面，在 7 列间管理 Agent 任务。

### 任务状态

| 状态 | 说明 |
|-------|-------------|
| **Backlog** | 等待调度 |
| **Ready** | 依赖已满足，可领取 |
| **Running** | Agent 正在执行 |
| **Completed** | 成功完成并验证 |
| **Failed** | 执行失败（自动重试或人工复核） |
| **Blocked** | 等待外部输入或依赖 |
| **Archived** | 已完成移出活跃板 |

### 角色化 Kanban LLM 工具

看板工具**默认不加载**，按场景 **Role Gate** 绑定，省 Token、降误调用：

| 场景 | 绑定工具集 | 数量 |
|------|-----------|-----:|
| 默认聊天（未勾选 Kanban） | 无 | 0 |
| 聊天启用 Kanban | orchestrator（add、list 含可选 stats、unblock） | 3 |
| 看板任务 Worker | worker（show/complete/block/heartbeat/comment/attach） | 6 |

看板创建/列表等 **Board CRUD 仅 REST/GUI**，不占用 LLM tool slot。用 `kanban_add_task.depends_on` 建 DAG 边；`kanban_list_tasks` 可选 `task_id` 单查任务与依赖，或 `include_stats=true` 获取板级计数。板级列表默认 **50 条**（上限 200），超出时返回 `truncated` 元数据，与 REST API 及 Hermes 行为一致。

Hermes 用户迁移后可保留 **worker / orchestrator** 分角色体验，并额外获得可视化看板、DAG 调度与 CompletionVerifier。OpenClaw 仅有展示看板、**0** LLM 工具；deer-flow / LobsterAI / CoPaw / jiuwenclaw 等 **无** 原生 Kanban LLM 工具。

### 看板附件一键可达

Worker 通过 **`kanban_attach`**（path/url，SSRF 安全）挂附件后，任务卡片显示 **📎 回形针 badge**——**点击即可打开任务抽屉**预览或下载，无需在日志或 CLI 里翻文件。竞品多为纯展示或只见计数。

### Chat↔Board 闭环（Lean CORE）

在 Chat 中启用 Kanban 后，`kanban_add_task` 成功会在对话流展示 **`KanbanTaskCreatedCard`**（标题、板名、状态、任务 ID），并持久化到消息的 `extra_data.kanban_tasks_created`，刷新或续聊后卡片仍在。

点击 **「在看板查看」** 会带 `source_chat_id` 打开过滤后的看板视图，只显示与本会话相关的任务。Pipeline/Decompose 拆出的子任务会继承 originating chat 的 `source_chat_id`，过滤视图完整。

| 能力 | Hermes | OpenClaw | Myrm |
|------|--------|----------|------|
| Chat 侧 Kanban 工具 | ✅ 模块化 @tools | ❌ 0 个 | ✅ orchestrator 3 工具（opt-in） |
| GUI 成功回执卡 | ❌ CLI 输出 | ❌ 无 | ✅ KanbanTaskCreatedCard |
| 一键跳过滤看板 | ❌ | ❌ | ✅ source_chat 深链 |
| 大板 list 防 token 爆炸 | ⚠️ 视配置 | N/A | ✅ 自动 scope + 50/200 limit |

**验证（2026-07-21）**：Chrome E2E #4（seed fixture → 成功卡 → 深链看板）+ Vitest TOOL_END 单元测试 + live agent-stream e2e 2/2。

### 自治认领（Worker 自动抢单）

常见 Agent Team 教程描述：**Lead 逐个手动分配**、Worker **每 5 秒轮询**、文件任务板 + 易竞态的 claim。Myrm 提供生产级替代：

| 教程痛点 | Myrm 你得到什么 |
|---------|----------------|
| Lead 任务逐个 assign | **Worker 自治认领** — 建好 DAG 即可，分派全自动 |
| 5s idle 轮询 | **事件驱动唤醒** — 毫秒级开跑，几乎零空转 CPU |
| 幽灵认领 / 文件锁 | **SQL 原子 claim** — 只有一个 Worker 成功，其余干净失败 |
| Lead 盯 CLI `[Inbox]` | **活动流 SSE** — promoted/completed/failed 实时可见，可选 IM 通知 |
| 同目录并发写冲突 | **每任务 Git Worktree** — 同仓库多 Agent 并行改码不覆盖 |

**迁移要点：** 保留「Lead 规划、Worker 执行」心智，但**不必再当调度员**；看板用共享状态协调，而非点对点命令。

**验证（2026-07-10）**：429 项 harness（96% 覆盖）+ 20 项 server 绑定 + live agent-stream e2e + Chrome 看板/聊天 UI 全绿。

**PTC 与 native 分工：** 单次搜网/检索用 **native** `web_search_tool` / `grep_tool`；仅当同一段 Python 需多次 RPC 并只回一行摘要时用 **PTC**（`bash_code_execute_tool`）。bash 说明已不再以 web 搜为例，避免误路由（与 Hermes「disabled 工具不出现在 schema」同理）。

### 任务结果编辑

已完成、失败或取消的任务，可直接在前端任务抽屉中编辑 `result` 和 `metadata` 字段。

- 点击任务卡片 → 打开抽屉 → 内联编辑结果
- 仅对终态任务（completed/failed/cancelled）开放，避免干扰运行中任务
- 每次编辑生成 `EDITED` 事件并记录变更字段，在活动流中提供完整审计轨迹
- metadata 采用增量合并策略，已有字段不会被意外覆盖

### 事件时间线与执行历史

任务抽屉包含完整的**事件时间线**和**运行历史**面板：

- **运行历史**：每次执行尝试展示结果状态（成功/失败/取消）、耗时、工作者 ID 和 Agent 摘要，失败时附带错误信息
- **事件时间线**：按时间排序的任务生命周期事件流，带颜色标记的徽章——用户评论、心跳注记、分支切换、验证失败、超时等，每个事件展示时间戳和 payload 详情
- **诊断**：健康规则（死锁依赖、长时间运行、过期任务）在卡片上以严重度徽章展示

### 流水线向导

复杂工作流用 **Pipeline Wizard** 从模板生成任务 DAG：

1. **看板 > New Pipeline**
2. 选择模板（或自建）
3. 向导生成带依赖的任务图
4. 审阅并启动 — 按依赖顺序执行

自定义模板在 Skill 文件 YAML frontmatter 中定义，可复用、可版本控制。

### Git Worktree 隔离

每个看板任务可选在隔离 Git worktree 运行：

- 并行 worker 同库无冲突编辑
- 每任务独立分支
- 完成可合并为 per-task PR

## 子 Agent 编排

单 Agent 不足时，子 Agent 系统支持多 Agent 协作（6 种模式 + 动态发现）。

### 动态发现与 @ 提及

类 Coze 的动态发现与委派：

- **动态名册**：`allow_discovery` 的 Agent 自动注册；主 Agent（Planner/Leader）经系统指令了解队友能力。
- **显式 @ 提及**：聊天输入 `@` 弹出 ReferenceMentionPopover，自动补全并显式标记。
- **强制关注**：被标记时后端注入 Forced Attention Directive，保证委派而非幻觉忽略。
- **说话者身份**：`memory_context_middleware` 为 AI 消息加 `[Agent: {Name}]` 前缀，消除「分裂脑」幻觉。

### 编排模式

| 模式 | 说明 | 场景 |
|---------|-------------|----------|
| **Spawn** | 单子 Agent 委派 | 旁路任务不阻塞父 Agent |
| **Chain** | 顺序 A → B → C | 顺序敏感的流水线 |
| **Batch** | 并行独立任务 | 多主题同时研究 |
| **DAG** | 有向图与依赖 | 复杂前置条件工作流 |
| **Verified** | Worker + 独立 Verifier | 需交叉验证的关键任务 |
| **Swarm Fission** | 自主分裂/合并 | 可动态_spawn 的探索任务 |
| **Alternatives** | N 个 Agent 竞争生成方案 | 多方案对比，用户选择最优 |

### Verified 模式（对抗验证与零信任）

防 Agent「自评」或幻觉成功：

1. **Worker** 执行任务
2. **工作区 Diff 注入**：系统自动在 Worker 执行前后对工作区做 stat 快照，将文件变更差异（新增/修改/删除）注入 Verifier 的审查提示中，无论 Worker 是否汇报均可见
3. **物理证据**：须返回结构化 `verifiable_credentials`（文件路径、CLI 退出码等），仅自然语言宣称 PASS 会被判 FAIL
4. **Verifier** 在只读沙箱独立审查结果、工作区差异与证据
5. 验证失败则 Worker 按 Verifier 反馈重试
6. **验证结果实时推送**：每轮验证发射结构化 `VERIFICATION_VERDICT` SSE 事件，前端在聊天进度中展示 PASS/FAIL 状态、置信度和 findings 摘要
7. 最大重试可配置

根除「幻觉式成功」。

### 预算控制与熔断

| 维度 | 说明 |
|-----------|-------------|
| `max_descendants` | 最大子 Agent 总数（默认 20） |
| `max_children_per_agent` | 每 Agent 最大直接子节点（默认 5） |
| `max_spawn_depth` | 最大嵌套深度 |
| `context_budget` | 每子 Agent 独立 Token 预算 |
| `budget_tokens` / `max_cost_usd` | 硬性花费上限 |
| `max_agent_iterations` | **熔断**：物理限制迭代步数防无限循环 |

**智能模型降级**：预算将尽时可自动从昂贵推理模型降到更便宜模型，仍尝试完成任务。预算耗尽产生结构化错误，非静默失败。

### 工作区隔离与 UI 黑名单

每个子 Agent 在隔离工作区与系统沙箱运行：

- **CoW 克隆** — 写时复制工作区
- **精确同步** — 仅修改文件回传
- **.git 保护** — Git 目录排除操作
- **三层自动 GC** — 每 6 小时 + 启动时自动回收过期事件、运行记录和工作区目录，harness 目录边界安全校验防误删，DB 路径置 NULL 避免重复扫描——零运维
- **UI 交互黑名单** — 后台子 Agent 物理屏蔽 `interactive_feedback`、`send_message`，不会弹窗打断用户

### 行级冲突检测

多个子 Agent 并发操作同一代码库时，Myrm 通过行级冲突检测防止文件损坏：

- **写前检测** — 每次文件写入前检查是否有其他 Agent 最近修改过同一文件的重叠行范围
- **双级别响应** — 行范围重叠触发阻断错误（阻止写入），同一文件不同区域的编辑仅产生非阻断警告
- **零网络开销** — 冲突检测完全在 harness 层内运行，无需控制平面往返
- **自动清理** — 子 Agent 完成后，其文件活动记录自动清除

这种方法严格优于某些竞品使用的语义距离碰撞检测——它基于精确行范围而非近似语义距离。

### 无缝人工介入（HITL）

检查点或需审批时 UI 弹窗。除接受/拒绝外支持**上下文注入**：用户可附加文字（「等等，颜色改成红色」），Agent 无缝续跑。

### 非致命超时

大多数 Agent 框架在子 Agent 超时后直接强杀——所有进度归零，只能从头再来。

Myrm 采用截然不同的方案：**超时的子 Agent 继续在后台运行**。

- 父 Agent 收到 `still_running: true` 的部分结果，可立即处理其他任务
- 子 Agent 完成后，**事件驱动回调**自动唤醒父 Agent——无需轮询、无需手动检查
- 已完成结果在父 Agent 下一轮可用，序列化语义干净（无误导性的完成时间戳）
- **3 种取消策略**（立即 / 优雅 / 检查点）按需精细控制是否终止子 Agent

**对你意味着什么：** 长时间的研究、代码生成、复杂分析永远不会因为武断的超时而丢失进度。你的 Agent 团队像真正的团队一样工作——有人慢了，团队继续推进，结果出来后自动衔接。

## 完成验证

看板或对话任务完成前，系统自动执行分层验证，防止 Agent 幻觉式「宣称成功」。

### CompletionVerifier 协议

验证结果含 `passed`（是否通过）、`reason`（判定理由）、`error_logs`（具体错误日志）。

### 分层验证策略

目标支持成本优化的分层验证：

1. **Shell 硬指标验证（零 LLM 成本）** — 在沙箱内执行客观命令（如 `test -f /output.csv`、`curl -sf localhost:8080/health`）。失败立即拒绝，无需调用 LLM。
2. **LLM 语义验证（仅在 Shell 全部通过后触发）** — 独立 LLM 评估结果是否满足验收标准，捕获主观质量问题。

这种分层策略在客观可验证的场景下消除 LLM 成本，同时保留语义深度评估能力。

## 任务诊断

内置诊断引擎主动发现不健康任务并给出建议。

### 6 条诊断规则

| 规则 | 检测 | 动作 |
|------|---------|--------|
| **Stranded in Ready** | READY 过久未领取 | 归档或查调度器 |
| **Repeated Failures** | 连续失败过多 | 复核描述或归档 |
| **Stuck in Blocked** | BLOCKED 过久 | 评论、解阻或归档 |
| **Dead Dependency** | 父任务全终态失败/归档 | 归档孤儿任务 |
| **Stranded in Triage** | TRIAGE 粗略想法久未细化 | Specify 或归档 |
| **Block→Unblock Cycling** | 反复阻塞解阻根因未解决 | 复核阻塞原因 |

### 严重度自动升级

Warning（1–2× 阈值）→ Error（2–7×）→ Critical（≥7×），看板卡片显示徽章，点击查看详情与一键操作。

## 上手

1. 侧栏打开看板
2. **New Task** 描述待办
3. 拖线定义依赖
4. 启动 — 按优先级与依赖自动执行
5. 心跳实时监控

描述复杂任务给任意 Agent，它会自动分解并按合适模式委派。

**实测验证**：Kanban harness **429 项**（含 list limit/truncated）+ sub_agents **780 项**专项测试 100% 通过，叠加 server Kanban 集成 **10 项** + live agent-stream e2e **1 项** + 前端 **110 项**共计 1800+ 项。8 态生命周期 + 19 种事件（StrEnum 类型安全）。事件驱动调度毫秒级响应 vs 竞品 60 秒轮询。（2026-07-10 实测）
