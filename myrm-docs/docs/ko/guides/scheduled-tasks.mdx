# 예약된 작업

자연어 설명을 사용하여 반복 작업을 만듭니다. Myrm의 크론 시스템은 세 가지 스케줄링 모드, 작업 연결, 상황 보고 및 10계층 소음 방지 방어를 지원합니다. 이는 기본 크론 스케줄링을 훨씬 뛰어넘는 수준입니다.

## 작업 만들기

### 채팅을 통해(자연어)

어떤 대화에서든 자연스럽게 일정을 설명하세요.

> "매일 아침 9시에 경쟁사 가격을 긁어 비교 보고서를 이메일로 보내주세요."

에이전트는 자동으로 예약 의도를 감지하고 승인 카드를 제시합니다. 일단 확인하면 작업이 즉시 생성됩니다. 작업 이름, 일정, 다음 실행 시간, 바인딩된 모델을 보여주는 구조화된 작업 카드가 채팅에 표시되며 관리 대시보드로 이동할 수 있는 버튼도 있습니다. 또한 에이전트는 내장된 최고의 청사진 템플릿을 자동으로 일치시켜 작업 품질을 향상시킵니다. 반복 일정은 실수로 생성되는 것을 방지하기 위해 명시적인 확인이 필요합니다.

### Cron 도구 모드(에이전트 구성)

기본적으로 cron 관리는 **검색 가능**합니다. 이는 Turn1 도구 스키마(~0 cron 토큰)를 차지하지 않습니다. 채팅에서 일정을 설명하면 Myrm은 요청 시 `cron_manage_tool`을 로드합니다.

| Setting | Turn1 tools | Best for |
|---------|-------------|----------|
| **Cron OFF** (default) | Discover on intent | Everyday chat — lean token footprint, prompt-cache friendly |
| **Cron ON** in Agent built-in tools | Eager Turn1 (~827 tok) | Power users who want cron callable every turn without discovery |

**에이전트 구성 → 내장 도구 → 예약된 작업(Cron)**에서 활성화 또는 비활성화합니다. 크론 권한이 없는 클라우드/샌드박스 계획에서는 업그레이드 링크를 통해 토글이 비활성화됩니다. 동일한 규칙이 GUI, REST API 및 에이전트 경로에 적용됩니다.

검색(기본값) 모드와 열성 모드 모두 자동화된 테스트와 실제 모델 WebUI 엔드투엔드 검증으로 처리됩니다.

### GUI을(를) 통해

**설정 > 예약된 작업**으로 이동하고 **만들기**를 클릭하여 일정 선택기, 모델 선택기, 배달 옵션이 포함된 시각적 구성 대화상자를 사용하세요. 원클릭 설정을 위해 **14개의 청사진 템플릿**(아침 브리핑, 주간 검토, Wiki 아침 델타, 나중에 읽기 수집 등) 중에서 선택하세요. 이는 에이전트가 API을 통해 사용하는 것과 동일한 템플릿입니다. `GET /cron/blueprints` API은 **en, zh, ja, de 및 ko**에 대해 현지화된 **제목**, **설명** 및 **프롬프트_템플릿**을 반환합니다. 카탈로그는 이 API에서만 로드됩니다(실패 시 재시도). 슬롯 라벨은 프런트엔드 언어 키를 사용합니다.

## 작업 유형

| Type | Description | LLM Cost |
|------|-------------|----------|
| **Agent** | Full AI agent execution with prompt, model, and memory | Token-based |
| **Shell** | Direct shell command (local/desktop only, hidden in cloud) | Free |
| **Script (Python)** | Sandboxed Python script with 60s timeout (works everywhere including cloud) | Free |

### 스크립트 모드(0 LLM 비용)

LLM 호출 없이 Python 코드를 실행하는 작업을 생성할 때 **스크립트(Python)**를 선택하세요. 스크립트는 60초 제한 시간으로 격리된 하위 프로세스에서 실행됩니다.

- **stdout이 출력이 됩니다** — 비어 있지 않은 출력은 구성된 채널로 전달되고, 빈 출력은 자동으로 건너뜁니다.
- **신호 건너뛰기**: 작업을 정상적으로 중단하려면 `[SKIP]` 또는 `{"action": "skip"}`을 인쇄하세요.
- **클라우드 안전**: 셸 명령과 달리 Python 스크립트는 모든 배포 모드(로컬, 데스크톱, 클라우드 샌드박스)에서 사용할 수 있습니다.
- **사용 사례**: API 상태 확인, 데이터 모니터링, RSS 필터링, 데이터베이스 감사

## 세 가지 스케줄링 모드

| Mode | Syntax | Example |
|------|--------|---------|
| **CRON** | Standard cron expression | `0 9 * * *` (daily 9 AM) |
| **INTERVAL** | Every N minutes (min 5) | `every_minutes=30` |
| **ONCE** | ISO 8601 one-shot | `2026-06-01T10:00:00` |

## 세션 모드

에이전트가 반복 실행 전반에 걸쳐 대화 컨텍스트를 처리하는 방법을 제어합니다.

| Mode | Behavior | Best for |
|------|----------|----------|
| **Isolated** (default) | Fresh context every run — no memory of previous executions | Independent one-off tasks |
| **Main** | Continues the agent's main chat thread (loads last 30 messages) | Tasks that need full conversation history |
| **Daily** | Automatically injects same-day run outputs into prompt; resets at midnight (UTC) | Hourly monitoring, trend detection, recurring data collection |

### 일일 모드 실행 중

작업이 **매일** 모드로 실행되는 경우:
1. 에이전트는 이전 당일 출력을 시간순으로 확인합니다(최대 5개 실행, 각각 500자로 잘림).
2. 새로운 날의 첫 번째 실행에는 어제의 최종 출력이 간략한 요약으로 포함됩니다.
3. 이를 통해 에이전트는 추세를 감지할 수 있습니다. 예: "CPU가 지난 3시간 동안 45% → 72% → 90% 증가했습니다."

일일 모드는 추가 저장 공간을 전혀 사용하지 않으며(기존 실행 기록 재사용) 프롬프트 캐시 효율성에 영향을 주지 않습니다.

## 태스크 체이닝(context_from)

한 작업의 출력이 다른 작업에 반영되도록 작업을 함께 연결합니다.

> "Task A는 일일 매출 데이터를 수집하고, Task B는 이를 분석하여 보고서를 생성합니다."

참조된 작업의 최근 성공적인 출력을 다음 작업의 프롬프트에 삽입하려면 `context_from`을 설정합니다.

## 하트비트 모니터링

**상황 보고서** 주입 기능이 포함된 주기적인 자가 점검(`__heartbeat__`) — 에이전트는 매 틱 전에 메모리 변경 사항, 보류 중인 알림, 기한 약속(후속 추적) 및 시스템 상태를 검토하여 블라인드 점검을 인텔리전스 기반 작업으로 전환합니다. 중복 알림을 방지하기 위해 예정된 약속은 자동으로 전달된 것으로 표시됩니다.

### 에이전트 바인딩

**설정 → 시스템 → 하트비트**에서 에이전트 프로필을 하트비트에 바인딩합니다. 하트비트는 바인딩된 에이전트의 모델, 시스템 프롬프트, 기술 및 도구 구성을 상속하므로 이를 별도로 구성할 필요가 없습니다.

- **드롭다운 하나**: 기본 제공 에이전트 또는 사용자 정의 에이전트 중에서 선택합니다.
- **모델 상속**: UI는 어떤 모델이 사용될지 보여줍니다(예: "사용 모델: openai/gpt-4o-mini").
- **바인딩 해제**: 바인딩을 지우려면 "기본 에이전트"로 다시 전환하세요. 하트비트는 전역 기본 모델로 되돌아갑니다.
- **에이전트 프로필 SSOT**: 에이전트 모델을 한 번 업데이트하면 바인딩된 모든 하트비트가 다음 실행 시 자동으로 새 모델을 사용합니다.

## 스케줄러 활성 대시보드

Cron 대시보드 상단의 실시간 시각적 표시기는 스케줄러 상태를 한눈에 보여줍니다.

| Status | Meaning | Visual |
|--------|---------|--------|
| **Green** | Healthy — scheduler running and ticking normally | Animated pulse dot |
| **Yellow** | Degraded — starting up, stale tick (>120s), or tick errors | Static amber dot |
| **Red** | Stopped — scheduler not running or missing timer | Static red dot |

배지는 30초마다 `GET /api/v1/cron/scheduler/health`을 폴링합니다. 브라우저 탭이 숨겨지면 자동으로 일시 중지되고 다시 전환하면 즉시 새로 고쳐지므로 다중 탭 워크플로에서 서버 리소스가 절약됩니다.

정확한 마지막 틱 타임스탬프와 오류 수를 보려면 배지 위로 마우스를 가져가세요.

## 스마트 배송

| Feature | Description |
|---------|-------------|
| **Multi-channel** | Results delivered via chat, webhook, Feishu, Slack, or any of 35+ channels |
| **Feishu/Lark bot hooks** | Custom bot webhook URLs (`open.feishu.cn` / `open.larksuite.com`) receive **`msg_type=text`** payloads — works out of the box; no OAuth chat_id wiring |
| **WeCom group bot hooks** | Paste a `qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...` URL — auto-detected, sends **`msgtype=markdown`** with bold headers and status emoji; retry with exponential backoff; validates `errcode` responses |

| **Failure alerts** | Separate `failure_webhook_url` for ops alerting |

### 스크립트 전달(인라인 채널 선택)

**스크립트(Python)** 작업을 생성할 때 대화 상자에 인라인 전달 대상 선택기가 표시됩니다.

1. **채팅**(기본값) - 출력이 작업 기록에 유지됩니다.
2. **연결된 IM 채널** — 구성된 통합에서 자동 검색됩니다(연결된 채널만 표시됨)
3. **대상 필드** — 선택한 채널에 따라 채팅 ID, 채널 이름 또는 웹훅 URL을 지정합니다.

이렇게 하면 별도의 전달 구성 페이지로 이동할 필요가 없습니다. LLM이 관련되어 있지 않으므로 스크립트 작업에 대해 모델 선택기가 자동으로 숨겨집니다.

## 배송 보증(선택 후 실행 검토)

**에이전트** 예약 작업(스크립트 전용 작업 아님)의 경우 에이전트별로 선택적 전달 검토를 활성화할 수 있습니다.

1. **설정 → 에이전트 → [내 에이전트] → 기능**을 엽니다.
2. **배달 보증**에서 **예약된 작업 확인**을 켭니다.
3. 저장 - 에이전트별로 설정이 유지됩니다(기본값은 꺼짐).

**활성화되면 어떻게 되나요?**

| Step | User-visible effect |
|------|---------------------|
| Cron run completes successfully | Run shows as successful (unchanged) |
| Run used side-effect tools (file write, bash, browser, etc.) | A built-in reviewer sub-agent runs afterward (≤ 120s, bounded by job timeout) |
| Review passes | Run history shows a **delivery review: pass** badge |
| Review fails | Run **still shows success**, but history adds an amber warning — task is not auto-retried |

**존재 이유:** 무인 작업은 부작용이 잘못된 동안 "완료"를 보고할 수 있습니다. 이를 통해 Cron 실행 목록에 구조화된 감사 추적이 제공됩니다. 경쟁업체는 일반적으로 **선택된 Cron 실행 메타데이터 + WebUI 배지**가 아닌 자동 턴엔드 가드 또는 목표 루브릭만 제공합니다.

**비용 관리:** 기본적으로 꺼져 있습니다. 읽기 전용 실행은 검토 건너뛰기입니다. 대화형 채팅은 영향을 받지 않습니다(추가 Turn1 도구 없음).

## 승인 기준(구조화된 출력 검증)

실행할 때마다 작업의 결과를 자동으로 확인하는 측정 가능한 품질 검사를 정의하세요. 배달 보증(LLM 기반 검토)과 달리 승인 기준은 **결정적**입니다. 즉, 성공/실패를 결정하는 셸 명령 또는 의미 체계 검사입니다.

### 기준 추가

GUI에서 작업을 생성하거나 편집할 때 **수락 기준** 섹션을 확장하세요(에이전트 유형 작업에만 해당).

1. **기준 추가**를 클릭합니다.
2. 유형 선택:
   - **Shell** — 성공(종료 코드 0)하거나 예상 출력과 일치해야 하는 셸 명령
   - **의미** — LLM 심사위원이 출력이 자연어 설명을 충족하는지 평가합니다.
3. 검사 내용을 설명하세요(예: "출력 JSON에 3개 이상의 항목이 있습니다." 또는 "보고서에 5개의 경쟁업체가 모두 언급되어 있습니다.")

### 작동 방식

| Path | Trigger | Mechanism |
|------|---------|-----------|
| **Goal queue** (active goal exists) | `create_goal(acceptance_criteria=...)` | Harness `VerificationGatekeeper` runs after goal completion |
| **Direct execution** (no active goal) | Post-run in `_run_once` | `acceptance_verification.py` bridges `VerificationGatekeeper` |

두 경로 모두 하네스 프레임워크에서 동일한 `VerificationGatekeeper`을 사용합니다. 기준은 실행 모드에 관계없이 동일하게 평가됩니다.

### 실패 동작

- **하나라도** 기준이 실패하는 경우 → 실행 상태가 **FAIL**로 표시됩니다.
- 실패 전달(구성된 경고 채널)이 트리거됩니다.
- 작업이 자동으로 재시도되지 **않습니다**(일반 실패와 동일)

### 예

허용 기준이 포함된 일일 가격 스크레이퍼:

| Type | Description |
|------|-------------|
| Shell | `jq '.items \| length' /tmp/prices.json` must output `>=3` |
| Semantic | "Report includes pricing data for all monitored competitors" |

사이트 변경으로 인해 스크레이퍼가 경쟁사 3개 중 2개만 가져오는 경우 셸 검사는 즉시 실패합니다. 며칠 후 누락된 데이터를 발견하는 대신 경고가 표시됩니다.

### API 지원

`POST /cron/jobs` 및 `PATCH /cron/jobs/:id` 엔드포인트는 `acceptance_criteria` 배열을 허용합니다.

```json
{
  "acceptance_criteria": [
    { "type": "shell", "description": "jq '.count' output.json >= 5" },
    { "type": "semantic", "description": "Summary covers all key metrics" }
  ]
}
```

## 10단 소음방지 방어

| Layer | Mechanism | Effect |
|-------|-----------|--------|
| 1 | Active Hours | Only runs within configured time window |
| 2 | [SILENT] instruction | AI self-judges no-value content, skips push |
| 3 | Output Hash dedup | Identical results not re-pushed |
| 4 | Cooldown period | Enforced minimum interval between pushes |
| 5 | Max Fires limit | Auto-stops after N executions, push notification sent |
| 6 | Skip If Active | Won't spawn new instance while previous runs |
| 7 | Expires At | Auto-stops at expiration datetime, push notification sent |
| 8 | PreFlight Condition | Sandboxed probe script must pass before execution |
| 9 | No-content Skip | Heartbeat skips LLM call when all sections empty |
| 10 | Failure Alert Cooldown | Even failure alerts have cooldown periods |

## 증분 모니터링

작업이 완전히 새로운 콘텐츠만 보고하도록 지능형 델타 감지를 활성화합니다.

| Setting | Purpose |
|---------|---------|
| `monitor_config.enabled` | Activates incremental monitoring |
| `monitor_config.ttl_days` | Baseline auto-resets after this TTL |

활성화되면 시스템은 현재 출력과 저장된 기준선 간의 델타를 계산합니다. 새로운 콘텐츠가 감지되지 않으면 전송을 자동으로 건너뜁니다(exit_code=0). 실제로 새로운 정보만 알림을 트리거하며(exit_code=1), 델타만 채널에 전달됩니다.

TTL 만료 후 기준선 자동 재설정을 통해 장기 실행 모니터가 오래된 상태를 누적하지 않도록 합니다.

**에이전트 대화 제어:** 모니터링은 대화를 통해 완전히 구성할 수 있습니다. 세트 기반 모니터링을 활성화하려면 에이전트에게 "가격 변동 시에만 알림"을, 비활성화하려면 "매번 알림"을 ​​지정하세요. 에이전트는 `monitor_type` 값 `set`, `hash`, `timeseries` 및 `off`(비활성화)를 지원합니다.

## 무결성 검증(머클체인)

모든 실행은 SHA-256을 사용하여 이전 실행과 해시 체인으로 연결되어 변조 방지 감사 추적을 생성합니다.

- `POST /api/v1/cron/{job_id}/verify-integrity`을 통해 체인 무결성을 확인합니다.
- 간격(실행 누락), 변조(수정된 출력) 또는 재정렬을 감지합니다.
- 기업 규정 준수: 예약된 작업이 예상대로 실행되었다는 암호화 증명

## 이벤트 기반 트리거

시간 기반 일정 외에도 외부 이벤트에 의해 작업이 트리거될 수 있습니다.

| Trigger Type | How It Works |
|-------------|-------------|
| **Event Regex** | Incoming IM channel messages matching a regex pattern trigger the task — configured in the GUI, no webhook URL required |
| **System Event** | Structured events (source + event_type + filters) trigger automatically |
| **Webhook** | External services send HTTP POST with HMAC-SHA256 signature verification |
| **Stream (WS/SSE)** | Outbound WebSocket or Server-Sent Events connection — listens for real-time events from external services. Works behind NAT/firewall without exposing a public URL. Supports JSONPath + regex filtering, auto-reconnect with exponential backoff. |
| **Poll** | Periodic HTTP GET with content-hash change detection — fires only when the response content changes. Supports JSONPath field extraction for targeted monitoring. |

트리거 컨텍스트(일치하는 메시지, 이벤트 페이로드, 웹후크 본문, 스트림 데이터 또는 폴링된 콘텐츠)가 에이전트의 프롬프트에 삽입되므로 트리거된 *이유*를 알 수 있습니다.

### IM 메시지 → 이벤트 트리거(아키텍처)

연결된 채널(Feishu, Telegram, Slack 등)의 인바운드 메시지는 이벤트에 의해 트리거되는 크론 작업을 자동으로 실행할 수 있습니다.

1. 설정에서 **채널 연결** — 장기 연결 또는 웹훅 수신
2. **이벤트** 트리거 유형으로 **작업 만들기** — 채널 필터 및 정규식 패턴 설정
3. `AgentRouter`을 통한 **메시지 흐름** — 명령(`/stop`, `/new`), 반응 및 보류 중인 승인을 건너뜁니다. 일치하는 메시지는 한 번 발송됩니다.

:::tip Cloud & Local Parity
클라우드 배포에서 제어 플레인 수신 엔드포인트는 메시지만 대기열에 추가합니다. 이벤트 발송은 샌드박스 라우터에서 발생하므로 두 레이어가 모두 발송될 경우 발생할 수 있는 중복 트리거를 방지합니다.
:::

**테스트된 시나리오:** 일반 디스패치, 명령 건너뛰기, 승인 건너뛰기, 반응 건너뛰기, 중복 메시지 중복 제거 — 16개의 자동화된 테스트가 전체 경로를 확인합니다.

### 원격 노드 이벤트(모바일/IoT 자동화)

외부 시스템은 HTTP를 통해 에이전트에 구조화된 이벤트를 보고할 수 있습니다. 상시 연결이 필요 없고 SDK도 필요하지 않습니다.

```bash
curl -X POST https://your-myrm.example/api/v1/remote-access/node/events \
  -H "Authorization: Bearer <pair_token>" \
  -H "Content-Type: application/json" \
  -d '{"source": "ios_shortcuts", "event_type": "location_arrived", "payload": {"location": "home"}}'
```

| Field | Description |
|-------|-------------|
| `source` | Identifier of the reporting system (e.g., `ios_shortcuts`, `android_tasker`, `home_assistant`) |
| `event_type` | The event name (e.g., `location_arrived`, `wifi_connected`, `battery_low`) |
| `payload` | Arbitrary JSON context passed to the triggered Agent task |

**인증:** QR 코드 페어링 또는 활성 WebUI 세션을 통해 발급된 유효한 `pair_token`(hub_list 범위)이 필요합니다.

**설정 방법:**
1. 설정 → 원격 액세스 → QR 코드를 통해 모바일 장치를 페어링하세요.
2. 트리거 유형 **시스템 이벤트**를 사용하여 예약된 작업을 생성합니다. 소스 및 event_type 필터를 설정합니다.
3. 이벤트를 엔드포인트에 POST하도록 iOS 바로가기/Android Tasker/Home Assistant 구성

이벤트는 구성된 SystemEventTrigger 규칙과 자동으로 일치하고 페이로드가 컨텍스트로 삽입된 바인딩된 에이전트 작업을 실행합니다. 분당 요청 60개로 속도가 제한됩니다.

:::tip Zero Battery Drain
지속적인 WebSocket 연결(배터리 소모 및 백그라운드 연결 유지 해킹 필요)이 필요한 경쟁업체와 달리, 우리의 HTTP 기반 접근 방식은 이벤트가 발생할 때만 실행됩니다. 유휴 전력 소비는 전혀 없습니다.
:::

## 충돌 복구

Myrm의 스케줄러는 3단계 시작 복구를 통해 예기치 않게 다시 시작된 후 자동 복구됩니다.

1. **부실 실행 복구** — 완료되지 않은(프로세스 충돌) "실행 중"으로 표시된 작업을 감지하고 일정을 변경합니다.
2. **Missed-Slot Replay** — 다운타임 중에 누락된 크론 슬롯을 식별하고 이를 재생합니다.
3. **유예 기간** — 실화 유예 기간 내의 작업은 즉시 실행됩니다. 만료된 항목은 다음 주기로 건너뜁니다.

## 보안

- **기본적으로 페일클로즈됨**: `required_capabilities`이 선언되지 않은 작업은 명확한 지침에 따라 셸/코드/MCP 실행이 거부됩니다.
- **작업별 기능 펜스**: 각 작업은 필요한 권한(`shell_exec`, `file_write`, `mcp_invoke` 등)을 독립적으로 선언합니다. 선언된 기능은 사전 승인되고 선언되지 않은 기능은 거부됩니다.
- **블록 수준 절대 거부**: 파괴적인 명령(`rm -rf /`, `sudo`, `DROP DATABASE` 등)은 승인된 기능 내에서도 항상 거부됩니다.
- 매 실행 전 **신속한 주입 스캐닝**(12개 패턴)
- **ContextVar 자체 예약 가드**는 무한 작업 체인을 방지합니다(크론 작업은 새 크론 작업을 생성할 수 없음).
- **예산 집행**은 일일예산 초과 시 집행을 차단합니다.
- 이벤트 트리거 정규식 패턴에 대한 **ReDoS 보호**
- 웹훅 전달 URL에 대한 **SSRF 보호**

## 데스크탑 전원 관리

Tauri 데스크탑에서 예약된 작업은 실행 중 시스템 절전을 방지하기 위해 자동으로 **PowerLock**을 획득합니다.

- **macOS**: `caffeinate` 하위 프로세스
- **리눅스**: `systemd-inhibit`
- **윈도우**: `SetThreadExecutionState`

잠금은 RAII로 보호되며 작업이 완료되면(실패하더라도) 자동 해제됩니다.

## 청사진 템플릿(원클릭 설정)

사전 구축된 템플릿을 사용하여 3번의 클릭만으로 일반적인 자동화 작업을 생성하세요. **예약된 작업 > 생성 > 템플릿에서**로 이동하여 사용 가능한 청사진을 찾아보세요.

| Blueprint | Category | Slots | Description |
|-----------|----------|-------|-------------|
| Morning Briefing | Productivity | time, weekdays | Daily briefing on news, weather, and reminders |
| Weekly Review | Productivity | time, day | Summarize weekly progress and plan ahead |
| Custom Reminder | Personal | time, message | Recurring reminder with your own message |
| News Digest | Information | time, weekdays, topic | Curated news digest on chosen topics |
| Evening Winddown | Personal | time, weekdays | Calming daily summary and tomorrow's preview |
| Local Health Check | DevOps | time, weekdays | Monitor system CPU, memory, and disk |
| Competitor Watch | Business | time, day, competitors | Track competitor news and product updates |
| Habit Check-in | Personal | time, habits | Daily habit tracking with streak awareness |
| Daily Learning | Education | time, weekdays, subject | Get a curated learning topic each day |
| **Social Media Watch** | Business | time, weekdays, brand, platforms, keywords (optional) | Monitor brand mentions and sentiment across social platforms |
| **Read-it-Later Ingestion** | Productivity | time, weekdays | Auto-ingest saved articles into your knowledge base daily |
| **Wiki Morning Delta** | Productivity | time, weekdays | Daily vault change digest (≤3 lines); skips delivery when nothing changed (`[SILENT]`) |

**두 번째 브레인 빠른 시작(설정 → Wiki):** 한 번의 클릭으로 미리 설정된 에이전트와 **둘 다** Read-it-Later(06:00) 및 Wiki Morning Delta(07:00) 크론 작업이 적용됩니다. 수동 청사진 연결이 필요하지 않습니다. 크론이 하나만 있는 이전 사전 설정 버전을 적용한 경우 재적용은 멱등성을 갖습니다.

브라우저 자동화를 사용한 자동화된 브랜드 모니터링 — 공개 API이 없는 플랫폼(Xiaohongshu, Weibo, Twitter/X, LinkedIn, Douyin)에서 작동합니다.

**설정:** 소셜 미디어 워치 템플릿 선택 → 브랜드 이름 및 타겟 플랫폼 입력 → 키워드는 선택 사항(브랜드 전용 모니터링 작업) → 배송 채널 선택 → 완료.

**각 실행 작업:**
1. 브라우저 자동화를 통해 대상 플랫폼을 탐색합니다.
2. 구성된 키워드를 사용하여 언급된 브랜드를 검색합니다.
3. 감정 분류(긍정적/중립적/부정적)
4. 구조화된 인텔리전스 보고서 생성
5. 즉시 주의를 끌기 위해 매우 부정적인 게시물에 플래그를 지정합니다.
6. 구성된 IM 채널을 통해 전달합니다(또는 주목할 만한 내용이 없으면 침묵을 유지합니다).

**주요 이점:** API 종속 도구와 달리 브라우저 자동화는 로그인 세션이 있는 모든 플랫폼에서 작동합니다. API 키도 없고 속도 제한도 없으며 플랫폼이 API을 업데이트할 때 주요 변경 사항도 없습니다.
