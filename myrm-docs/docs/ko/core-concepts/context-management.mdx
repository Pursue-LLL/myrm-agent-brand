# 컨텍스트 관리

Myrm의 컨텍스트 관리 시스템은 에이전트가 정보 손실 없이 200회 이상의 대화를 유지할 수 있도록 보장하는 동시에 지능형 압축 및 캐시 최적화를 통해 비용을 낮게 유지합니다. 전체 파이프라인을 포괄하는 1,400개 이상의 자동화된 테스트를 통해 검증되었습니다.

## 아키텍처 개요

모든 메시지는 LLM에 도달하기 전에 12단계 점진적 오프로딩 파이프라인을 통과합니다.

```
User Message → Thinking Cleanup → Media Filter → Smart Filter → Active Tool Result Prune → Cache TTL Prune → Pre-Compact → Compress → Session Notes → Summarize → Post-Compaction Reread → Normalize → Media Resolve → Prompt Cache Optimize → LLM
```

## 압축 파이프라인

### 레이어 0: 인텐트 기반 압축(CompressionIntent)

데이터가 제거되기 전에 파이프라인은 현재 사용자 쿼리와 최근 기록을 분석하여 보존해야 할 항목에 대한 맵인 **압축 의도**를 구축합니다.

- **포커스 파일**: 현재 쿼리에서 적극적으로 참조되는 파일 경로는 보호된 것으로 플래그가 지정됩니다.
- **포커스 모듈**: 활발하게 논의 중인 코드 모듈은 공격적인 압축으로부터 보호됩니다.
- **실패한 도구 복구**: 최근 실패한 도구 호출의 ID가 유지되므로 에이전트가 다시 시도하거나 실패를 설명할 수 있습니다.

이 의도는 모든 후속 레이어를 통해 흐르므로 압축으로 인해 사용자가 적극적으로 작업 중인 컨텍스트가 절대 파괴되지 않습니다. 경쟁업체에는 이 단계가 없습니다. 압축은 주제를 가리고 중요한 작업 컨텍스트를 삭제하는 경우가 많습니다.

### 레이어 1: 즉각적인 필터링(ContextBudgetGuard)

대규모 도구 출력(예: 파일 콘텐츠, 검색 결과)은 지능형 예산 가드에 의해 처리됩니다. 고정된 도구별 잘림 임계값을 설정하는 경쟁업체와 달리 Myrm은 전체적인 예산 관리를 사용합니다.

- **스마트 예외**: 파일 읽기/쓰기 도구는 "읽기→잘라내기→다시 읽기" 루프를 방지하기 위해 잘림을 우회합니다.
- **구조 인식**: JSON/XML/CSV 출력은 무차별 문자 자르기 대신 구조적 자르기(스키마 유지)를 사용합니다.
- **디스크 지속성**: 대용량 출력은 요약 + 에이전트에 반환된 경로와 함께 자동으로 디스크에 저장됩니다.
- **예측적 오버플로 보호**: 잘림 강도는 남은 토큰 예산에 따라 동적으로 조정됩니다.

### 레이어 1.5: 범용 도구 출력 인텔리전스(FilterProcessor)

터미널 명령뿐만 아니라 **모든 도구**(검색, API, 브라우저, MCP 등) 출력은 3계층 방어로 보호됩니다.

| Layer | Component | Trigger | Effect |
|-------|-----------|---------|--------|
| **L1** | 11 Bash command compressors + YAML declarative engine | Shell output | Smart compression for git/pytest/npm etc., preserving key information |
| **L2** | `FilterProcessor` + `SemanticFilter` / `StructuralFilter` | Any tool output >5K tokens (single) or >15K tokens (turn aggregate) | Structural content: zero-LLM-cost extraction (9 formats); Unstructured: lightweight LLM semantic summary |
| **L3** | `ContextBudgetGuard` | Single output >100K chars | Hard safety net: persist to disk + return summary reference |
| **L4** | `OversizedResultHandler` (MCP) | MCP tool output > `max_output_chars` | Vault spill: full content → ArtifactVault with `vault://` pointer + head/tail summary. Fallback: head-truncation if vault unavailable |

**도구 보호 화이트리스트**: `file_read_tool`, `file_edit_tool` 및 기타 중요한 도구는 "읽기→잘라내기→다시 읽기" 루프를 방지하기 위해 필터링에서 자동으로 제외됩니다.

**프롬프트 캐시 인식**: 세션 재개(Resume) 또는 인간 참여(HITL) 시나리오 중에 필터링을 자동으로 건너뛰어 기존 캐시 접두사를 보호합니다.

**멱등성 보장**: 모든 필터링 작업은 엄격하게 멱등성입니다. 동일한 입력은 항상 동일한 출력을 생성합니다. 이렇게 하면 도구 루프 반복에서 기록 메시지가 다르게 변경되지 않고 LLM 접두사 캐시 안정성이 유지됩니다. 캐시를 깨뜨리는 컨텍스트 종속 결과를 생성하는 집계 잘림이 제거되었습니다. 그 책임은 레이어 1.5 프루닝, L2 압축 및 단일 메시지 오버플로 처리로 처리됩니다.

**전체 콘텐츠 복구 가능**: 필터링된 모든 대규모 결과는 `.myrm/artifacts/tool_outputs/`에 유지됩니다. MCP 대형 출력은 `vault://` 포인터와 함께 ArtifactVault에 저장됩니다. 에이전트는 `file_read_tool(paths=["vault://..."])`를 통해 언제든지 원본 콘텐츠를 검색할 수 있습니다.

### 레이어 1.5: 활성 단계별 도구 결과 정리

각 LLM 호출 전에 2,048개 토큰을 초과하는 *이전에 완료된 단계*의 도구 결과는 **0 LLM 비용**으로 컴팩트 아카이브 자리 표시자로 자동으로 대체됩니다. 가장 최근 단계의 결과는 모델이 사용할 수 있도록 항상 보존됩니다. 보호된 도구(`file_read_tool` 등)는 정리에서 제외됩니다. 아카이브 오프로드가 실패하면 원본 콘텐츠가 유지됩니다(장애 방지). 이전에 보관된 자리 표시자는 후속 단계에서 중복된 오프로드 호출을 방지하기 위해 메모리에 캐시됩니다.

이는 L1 필터링(대규모 *단일* 결과 처리)과 L2 캐시 TTL 정리(캐시 만료 후에만 트리거) 사이의 간격을 채웁니다. 지속적인 다단계 실행 중에 모든 단계는 모든 이전 도구 결과에 대해 전체 토큰 가격을 지불하게 됩니다. 이 프로세서는 해당 낭비를 사전에 회수합니다.

### 레이어 2: 캐시 TTL 정리

만료된 캐시 콘텐츠는 자동으로 삭제됩니다. 이는 오래된 데이터가 귀중한 컨텍스트 창 공간을 소비하는 것을 방지합니다.

### 레이어 3: 우선순위 인식 압축

메시지는 네 가지 우선순위 계층으로 분류됩니다.

| Priority | Treatment |
|----------|-----------|
| **System Critical** | Never compressed (system prompt, user instructions) |
| **Active Task** | Compressed last (current tool results, active errors) |
| **Older Context** | Compressed earlier (previous conversation turns) |
| **Background** | Compressed first (stale outputs, resolved errors) |

세 가지 전략이 순서대로 적용됩니다: **Dedup**(정확한 중복 제거) → **Truncate**(장황한 출력 단축) → **Remove**(낮은 값 회전 삭제).

### 레이어 4: 구조화된 요약

압축만으로는 충분하지 않은 경우 LLM은 14개 필드(사용자 목표, 활성 작업, 완료된 작업, 오류, 결정, 아티팩트, 차단된 항목, 다음 단계 등)가 포함된 구조화된 요약을 생성하여 압축 기록을 대체합니다. SummaryAuditor는 품질을 검증하고 증분 병합을 통해 새로운 정보가 손실 없이 기존 요약에 포함되도록 합니다. 지속성 이전에 모든 요약 필드는 이중 수정(인증 정보 유출 감지 + PII 수정)을 거쳐 원시 메시지의 민감한 데이터가 압축된 기록에 남아 있지 않도록 합니다.

**작업 연속성 필드**: 요약에는 전용 `blocked_items`(최대 3개의 현재 차단기) 및 `next_steps`(최대 5개의 계획된 작업)이 포함됩니다. 이는 Lost-in-Middle 연구에 의해 식별된 높은 주의 영역(~80% 재현율)인 요약 메시지의 U-곡선 꼬리 영역에서 렌더링되어 에이전트가 압축 후 "진행을 방해하는 요소"와 "다음에 수행할 작업"을 정확하게 기억하도록 보장합니다.

**증분 병합 인텔리전스**: 새 요약이 기존 요약과 병합되면 해결된 차단 요소가 자동으로 제거되고 완료된 단계가 삭제되어 수동 개입 없이 핸드오프 컨텍스트를 최신 상태로 유지합니다.

### 레이어 4.5: 압축 후 다시 읽기

요약 후 `PostCompactionRereadProcessor`은 `ArtifactTracker`에서 가장 최근에 수정/생성된 상위 5개 파일을 자동으로 다시 읽고 최신 콘텐츠를 `HumanMessage`로 컨텍스트에 삽입합니다. 이렇게 하면 에이전트가 압축이 발생하기 전의 오래된 스냅샷이 아닌 압축 직후에 새로운 파일 콘텐츠를 갖게 됩니다.

- **동적 예산**: 컨텍스트 재팽창을 방지하기 위해 총 다시 읽는 콘텐츠는 토큰 50,000개로 제한됩니다.
- **Integrity Guard 동기화**: 다시 읽는 파일 경로는 `FileIntegrityGuard`에 자동으로 등록되어 "마지막 읽기 이후 수정된 파일" 잘못된 경보를 방지합니다.
- **프롬프트 캐시 안전**: 콘텐츠는 `HumanMessage`로 삽입되며 시스템 프롬프트 접두사는 절대 건드리지 않습니다.

이는 Claude Code 및 Codex에 문서화된 압축 후 다시 읽기 기능과 일치하는 동시에 경쟁업체에 없는 Guard 동기화를 추가합니다.

### 레이어 5: 캐시 최적화

공급자별 캐시 마커(Anthropic `cache_control`, Qwen 접두사 캐시)가 삽입되어 후속 요청에 대한 프롬프트 캐시 적중을 최대화합니다.

## 가역적 압축

압축된 콘텐츠를 영구적으로 삭제하는 경쟁업체와 달리 Myrm의 압축은 **되돌릴 수** 있습니다.

- 도구 출력은 삭제되지 않고 `.context/` 저장소로 오프로드됩니다.
- 아카이브 체크포인트는 압축 전 전체 상태를 캡처합니다.
- 요청 시 콘텐츠를 복원할 수 있습니다.

이는 에이전트가 압축 후에도 이전 세부정보를 "돌아볼" 수 있음을 의미합니다.

## 시스템 프롬프트 아키텍처

### 4가지 프롬프트 모드

Myrm은 각 LLM 호출에 주입된 시스템 명령의 밀도와 범위를 제어하는 ​​네 가지 프롬프트 모드를 지원합니다.

| Mode | Content | Use Case |
|------|---------|----------|
| **full** | Identity + obedience rules + response rules + security + task integrity + memory rules | Default for all conversations |
| **lean** | Identity + security + task integrity | Advanced users who want less AI intervention |
| **naked** | Security rules + tool guidance only | Full user control, minimal system overhead |
| **search** | Dedicated search prompt | Lightweight fast-search interactions |

각 모드는 시작 시 정적 문자열로 사전 구축되어 동일한 매개변수 조합이 항상 동일한 문자열 객체를 반환하도록 보장하여 사용자 전반에 걸쳐 KV 캐시 적중률을 극대화합니다.

### XML 태그가 지정된 규칙 격리

모든 시스템 프롬프트 규칙은 의미 체계 XML 태그로 래핑되어 LLMs가 규칙 경계를 정확하게 구문 분석하고 긴 세션 동안 주의 표류를 방지할 수 있습니다.

- **프레임워크 레이어**(`model_discipline.py`): `<agent_behavior_rules>`, `<tool_use_enforcement>`, `<execution_discipline>`(모델별), `<escalation_contract>`
- **비즈니스 계층**(`shared_rules.py`): `<security_rules>`, `<memory_rules>`, `<task_integrity>`, `<response_rules>`, `<desktop_control_rules>`, `<absolute_obedience_override>`
- **ID 레이어** (`general_agent_prompt.py`): `<identity>`, `<ruleset>`, `<tool_guidance>`
- **미들웨어 레이어**: `<user_instructions>`, `<workspace_context>`, `<cli_tools>`

### 모델별 실행 규율

다양한 LLM 제품군에는 알려진 고장 모드가 있습니다. Myrm은 모델별 분야 프롬프트를 통해 이러한 사항을 자동으로 수정합니다.

| Model Family | Corrections Applied |
|-------------|-------------------|
| GPT / Codex / Grok | Tool persistence, mandatory tool use, act-don't-ask |
| Gemini / Gemma | Absolute paths, parallel calls, non-interactive |
| Claude | Execute-when-instructed, reduce disclaimers |
| DeepSeek / Qwen / GLM | Reduce over-explanation, enforce tool calls |

이러한 수정 사항은 초기화 시 결정되며 세션 중에는 절대 변경되지 않습니다. KV 캐시에 완전히 안전합니다.

## 신속한 캐시 최적화

프롬프트 캐싱은 캐시 적중이 발생할 때 입력 토큰 비용을 최대 90%까지 줄여줍니다.

### 디자인 원칙

1. **정적/동적 분리** — 시스템 프롬프트가 동결됩니다(캐시 가능). 모든 동적 콘텐츠는 사용자 메시지에 포함됩니다.
2. **4레이어 안정 접두사** — 시스템 프롬프트 → 도구 → 작업 공간 규칙 → 첫 번째 사용자 메시지가 안정 접두사를 형성합니다.
3. **캐시 중단 감지** — `cache_break_detector`은 캐시 무효화를 적극적으로 모니터링하고 원인을 보고합니다.
4. **추가만 정책** — 기록 메시지는 절대 수정되지 않으며 접두사 안정성이 유지됩니다.
5. **캐시 안전 스킬 감쇠** — 스킬을 로드한 후 `tool_choice.allowed_tools`을 통해 도구 액세스가 좁아집니다. 바인딩된 도구 스키마 목록은 고정된 상태로 유지되므로 세션 중에 접두사 캐시가 무효화되지 않습니다.

### 캐시 예열 및 유휴 KeepAlive(제로 콜드 스타트)

Myrm은 세 가지 중요한 순간에 Anthropic/Qwen 서버 측 접두사 캐시를 자동으로 미리 준비합니다.

1. **에이전트 초기화** — 시스템 프롬프트가 구축된 직후 사용자가 계속 입력하는 동안 실행 후 잊어버리는 `max_tokens=0` 요청이 캐시를 시드합니다. 첫 번째 실제 메시지는 웜 캐시에 도달하여 TTFT를 최대 52%까지 줄입니다.
2. **압축 후** — 컨텍스트 압축이 메시지 목록을 다시 작성한 후 다음 메시지에서 캐시 누락을 방지하기 위해 새 접두사가 즉시 예열됩니다.
3. **유휴 상태 유지** — 에이전트가 4분 이상 유휴 상태이면 백그라운드 `CacheKeepAliveManager`이 4분마다 경량 프로브(입력 토큰 10개, 출력 0개)를 보내 공급자의 5분 TTL이 접두사 캐시를 제거하는 것을 방지합니다. 이를 통해 사용자가 생각이 멈춘 후 재개할 때 2~5초 콜드 재시작 대신 일관된 0.5~1초 TTFT를 보장합니다. 비용: ~$0.09/일/세션. 관리자는 활성 대화 중에 자동으로 일시 중지되고 LLM 장애 조치 중에 자신을 올바르게 교체합니다.

이는 독점 기능입니다. 경쟁 프레임워크에서는 즉각적인 캐시 사전 준비 또는 유휴 연결 유지를 구현하지 않습니다.

### 보호 기능

| Feature | Description |
|---------|-------------|
| **Hot Cache Bypass** | When cache is already warm, skip unnecessary compression to preserve hits |
| **Anti-Thrashing** | Detect and skip repeated low-yield compression cycles |
| **90% Safety Net** | Emergency compression at 90% context window utilization to prevent OOM |
| **Cache-TTL Archive** | Expired cache entries are archived (not deleted) for potential restoration |

### 도구 호출 선형 정렬

긴 대화에는 필연적으로 압축이 필요합니다. 하지만 메시지 압축으로 인해 AI 도구 호출과 결과 간의 연결이 끊어져서는 안 됩니다. Myrm은 3계층 아키텍처 보호를 제공합니다.

| Layer | Mechanism | When |
|-------|-----------|------|
| **L1: ID-based Grouping** | `tool_call_groups` pairs messages by `tool_call_id` (not position), handling cross-turn reuse | During compression selection |
| **L2: Integrity Guard** | Post-compaction validation removes orphan tool messages and trims partially-matched AI messages | After compression completes |
| **L3: Dangling-Call Repair** | Pre-LLM middleware inserts synthetic error results for interrupted/timed-out tool calls (covers 3 call sources) | Before every LLM invocation |

이는 세션 잘림 후 경쟁 프레임워크를 괴롭히는 `Tool message must follow tool_calls` API 거부를 제거합니다. 239개의 전용 테스트를 통해 검증되었습니다.

### 세션 선호도 라우팅(OpenAI)

OpenAI 모델의 경우 Myrm은 모든 요청에 ​​`prompt_cache_key` 라우팅 힌트를 자동으로 삽입합니다. 이렇게 하면 동일한 세션 내의 모든 호출이 동일한 추론 노드로 라우팅되어 자동 접두사 캐시 적중률이 최대화됩니다.

- **자동 감지** — 기본 OpenAI 엔드포인트를 사용할 때만 삽입됩니다(api.openai.com).
- **제로 구성** — 기존 세션 ID를 사용하므로 사용자 작업이 필요하지 않습니다.
- **하위 에이전트 전파** — 하위 에이전트는 Python ContextVar를 통해 라우팅 키를 상속합니다.
- **효과** — 캐시 적중률이 ~60%에서 ~87%로 향상됩니다(OpenAI 문서화된 수치).

이는 경쟁 프레임워크(hermes-agent, openclaw)에서 사용되는 프로덕션에서 입증된 최적화입니다. Myrm은(는) OpenAI 제공자가 아닌 경우 부작용 없이 ~25줄로 이를 구현합니다.

## 생각하는 콘텐츠 관리

추론/사고 모델(DeepSeek, MiMo, Kimi, Anthropic Claude)을 사용할 때 `ThinkingBlockCleaner` 프로세서는 `reasoning_content` 및 `thinking_blocks`을 자동으로 관리하여 컨텍스트 팽창을 방지합니다.

- **인류 모델** — `reasoning_content`이 제거되었습니다(`thinking_blocks`과 중복됨). `thinking_blocks`는 보존됩니다
- **DeepSeek/MiMo/Kimi** — 이전 차례(마지막 사용자 메시지 전)의 기록 `reasoning_content`은 선택적으로 제거됩니다. 단, `tool_calls`(API 요구 사항)을 전달하는 메시지는 **제외**됩니다. 현재 회전 추론은 항상 보존됩니다.
- **모델 전환** — 세션 도중에 비사고 모델에서 사고 모델로 전환할 때 빈 `reasoning_content` 필드가 자동으로 기록 보조 메시지에 다시 채워져 400 오류를 방지합니다.

일반적인 20턴 DeepSeek 세션에서 이는 ~8,000~20,000개의 추론 토큰(추론 오버헤드의 ~50%)을 절약합니다.

## 극한 시나리오 방폭

대규모 컨텍스트 축적 및 다중 모드 자율 작업 중에도 탁월한 안정성을 보장하기 위해 Myrm은 4층 보호 해자를 사용합니다.

### 1. 게이트웨이 위생(토큰 블록)

요청이 에이전트 하네스에 도달하기 전에 제어 플레인 게이트웨이는 페이로드 크기를 스캔합니다. 대규모 악성 또는 잘못된 형식의 페이로드(>120K 토큰)는 `400 Bad Request`을 통해 즉시 차단됩니다. 이렇게 하면 LLM 컴퓨팅 노드에서 OOM(메모리 부족) 충돌 및 시스템 중단이 발생하는 것을 방지할 수 있습니다.

### 2. 보조 비율 쉴드(우아한 저하)

기본 모델(예: 200K 창)이 한계에 가까워지면 보조 모델을 사용하여 컨텍스트가 압축됩니다. 사용자가 지나치게 작은 보조 모델(예: 8K 창)을 구성한 경우 100K 토큰을 전달하면 치명적인 충돌이 발생하고 대화 기록이 손실됩니다. Myrm은 이 비율을 동적으로 확인합니다. 보조 모델이 너무 작으면 자동으로 성능이 저하되고 요약을 위해 기본 모델을 사용하여 경고를 표시하지만 세션은 활성 상태로 유지합니다.

### 3. 스마트 미디어 스트리핑

자율적으로 작동하는 비전 모델(예: 컴퓨터 사용)의 경우 스크린샷이 많이 추가됩니다. Myrm은 이전 기록에서 모든 대형 Base64 이미지를 제거하는 동시에 시각적 추론을 위해 마지막 2개의 미디어 포함 메시지만 유지하는 **슬라이딩 시각적 증거 창**을 구현합니다. 이는 비전 기능을 유지하면서 토큰 팽창을 대폭 줄여줍니다.

### 4. 꼬리 예산 비율

메시지를 임의로 자르는 대신 Myrm은 가장 최근 대화 꼬리에만 예약된 전용 토큰 예산(예: 최대 컨텍스트의 20%)을 계산합니다. 이를 통해 에이전트의 현재 작업 메모리와 활성 도구 결과가 압축되거나 압착되지 않고 작업 연속성이 보장됩니다.

## 하위 에이전트 결과 증류

하위 에이전트가 작업(예: 테스트 스위트 실행, 코드베이스 조사)을 실행할 때 원시 출력은 수천 줄이 될 수 있습니다. Myrm은 상위 에이전트의 컨텍스트가 깨끗하게 유지되도록 3계층 점진적 보호를 적용합니다.

| Tier | Mechanism | Effect |
|------|-----------|--------|
| **Tier 1** | `truncate_result` | Hard limit by `max_result_tokens` (last line of defense) |
| **Tier 2** | `_auto_vault_or_truncate` | Outputs exceeding 8,000 chars are stored in ArtifactVault; parent receives a compact summary (head + tail), a `vault://` pointer, and an explicit **`file_read_tool(paths=["vault://…"])` recovery hint** |
| **Tier 3** | `AgentHandoverState` | Structured handover (completed tasks, pending todos, risks, relevant files) is extracted and separated from the raw result |

또한 하위 에이전트는 `enable_context_compression`을 통해 **전체 컨텍스트 파이프라인을 상속**하므로 내부 실행은 이미 동일한 압축, 정리 및 요약 레이어의 이점을 활용하여 애초에 부풀려진 결과가 형성되는 것을 방지합니다.

**하위 에이전트 압축 안전성**: 하위 에이전트의 컨텍스트가 압축되면 동일한 파이프라인 보호가 적용됩니다. — `extract_protected_head`은 선행 시스템 메시지를 보존하고, 요약은 프롬프트 캐시를 보존하기 위해 `HumanMessage`(`SystemMessage` 아님)으로 삽입되며, `ensure_tool_pair_integrity`은 메시지 구조의 유효성을 검사합니다. 이는 하위 에이전트 컨텍스트가 압축 후 항상 유효한 시스템 메시지로 시작하여 경쟁 프레임워크에서 볼 수 있는 "보조 우선 거부" 실패 패턴을 제거함을 의미합니다.

**이것이 중요한 이유**: 경쟁업체는 "주 에이전트가 결과만 볼 수 있도록 하위 에이전트가 긴 로그를 처리하도록 하는 것"을 목표로 설명합니다. Myrm은(는) 이미 정보 손실이 없고(`vault://` URI의 `file_read_tool`, 회선 범위 지원) 구조화된 핸드오버 상태로 이를 구현하고 있습니다. 채팅 UI에는 보관된 결과에 대한 **VaultArtifactCard**가 표시됩니다. 추가 LLM 볼트 도구가 필요하지 않습니다.

## 보조모델 가드

요약을 위해 더 작은 LLM을 사용하는 경우 Myrm은 보조 모델의 컨텍스트 창을 동적으로 감지하고 보내기 전에 메시지를 자릅니다. 이렇게 하면 압축 중에 작은 모델이 충돌하는 것을 방지할 수 있습니다. 즉, 모든 입력 크기를 원활하게 처리합니다.

## 인간 앵커 보호

컨텍스트 압축 중에 사용자의 원래 명령(시스템 프롬프트 후 첫 번째 `HumanMessage`)은 시스템에서 생성된 합성 메시지(예: 압축 요약, 세션 메모)와 혼동되어서는 안 됩니다.

Myrm은 런타임 휴리스틱이 아닌 **구성별 수정 아키텍처**를 통해 이 문제를 해결합니다.

1. **실행 순서 보장**: `extract_protected_head()`은 합성 메시지(요약, 세션 메모, 사전 압축 회수)가 메시지 목록에 삽입되기 *전에* 실행됩니다. 이 기능은 실제 사용자 메시지만 볼 수 있습니다.
2. **역할 기반 격리**: 채팅 기록이 데이터베이스에서 다시 로드되면 `compacted_summary`이 `assistant` 역할 메시지(`AIMessage`)로 삽입되므로 보호 헤드 추출기에 의해 `HumanMessage`로 실수로 식별되는 일이 없습니다.
3. **심층 마커 방어**: 모든 합성 사용자 역할 메시지는 `UNVERIFIED_CONTEXT_MARKER` 및 `<memory-context>` / `<pre_compact_recall_context>` 태그를 전달하여 추가적인 의미 경계를 제공합니다.

**대 경쟁사**: Hermes은 `_is_real_user_message()`을 사용합니다. 이는 압축 주기마다 플래그 4개 + 접두사 5개 + 압축 메타데이터를 검사하는 최대 120줄의 런타임 검사기입니다. 이 접근 방식을 사용하려면 새로운 종합 메시지 유형이 추가될 때마다 검사기를 업데이트해야 하므로 유지 관리 부담이 발생하고 위험을 우회할 수 있습니다. Myrm의 아키텍처는 구조적으로 오인을 불가능하게 만듭니다.

## 7단 오버사이즈 출력 딥디펜스

도구 출력이 컨텍스트 창 예산을 초과하는 경우(예: 200KB JSON 응답, 50,000줄 테스트 로그) Myrm은 **7계층 심층 방어** 전략을 적용합니다. 각 계층은 자체 폴백을 통해 독립적으로 작동하여 데이터 손실이 없고 완전한 복구 가능성을 보장합니다.

| Layer | Component | Trigger | Strategy |
|-------|-----------|---------|----------|
| **L1** | MCP Vault Spill | MCP tool output > `max_output_chars` | Full content → ArtifactVault, return head+tail summary + `vault://` pointer + `file_read_tool` hint |
| **L2** | Subagent Auto-Vault | Subagent output > 8K chars | Same vault strategy + VaultArtifactCard UI in frontend |
| **L3** | Structure-Aware Trimming | JSON/text tool results | Preserve JSON skeleton (4-depth + 12-key + 6-item limits); text: head+tail retention |
| **L4** | Stream Recovery | `CONTEXT_OVERFLOW` from LLM API | Stage 1: emergency compact tool outputs → Stage 2: truncate oldest rounds |
| **L5** | Preflight Guard | Pre-request token estimation | Block request before API call if estimated tokens exceed threshold, preventing cost waste |
| **L6** | Hook Output Spiller | Hook output > 2500 tokens | Persist to disk + return truncated preview with file path |
| **L7** | Background Output Spill | Bash background command output | Auto-spill oversized background process output to disk |

**전체 데이터 보존**: 대용량 출력을 간단한 지침(원본 데이터 손실)으로 대체하거나 간단한 문자 잘림을 적용하는 경쟁업체와 달리 Myrm의 저장소 메커니즘은 원본 콘텐츠를 100% 유지합니다. 에이전트는 `file_read_tool(paths=["vault://..."], line_range="100:200")`을 통해 모든 부분을 검색할 수 있습니다.

**대 경쟁자**: nanobot은 도구 출력을 제한된 명령으로 대체하는 단일 레이어 "in-flight context Governor"를 사용합니다. 즉, 원본 데이터가 손실됩니다. OpenClaw는 파일 유출과 함께 2계층 잘림(결과당 + 집계 예산)을 사용합니다. 기능은 작동하지만 볼트 프로토콜과 프런트엔드 시각화가 부족합니다. Myrm의 7계층 접근 방식은 모든 도구 경로(MCP, bash, 브라우저, 하위 에이전트, 후크)가 독립적인 폴백 체인을 통한 전용 보호를 보장합니다.

## 실시간 복구 진행 피드백

긴급 상황 복구가 발생하는 경우(오버플로, 모델 오류) 사용자는 자동으로 "정지"되는 현상을 경험하지 않습니다. Myrm은 세분화된 진단 진행 상황을 실시간으로 프런트엔드로 스트리밍합니다.

### 단계 키

| Step Key | Trigger | User Sees |
|----------|---------|-----------|
| `context_compaction` | Emergency LLM-based compression | "Compressing context..." |
| `context_truncation` | Oldest rounds removed to fit window | "Trimming old context to fit window" |
| `model_failover` | Primary model overflows, switching to backup | "Context too long, switched to backup model" |
| `transient_retry` | Transient API error, auto-retrying | "Retrying..." |

### 결정적 폴백

LLM 기반 요약기가 실패하는 경우(네트워크 오류, 시간 초과, 인증 실패) **결정론적 대체**는 즉시 LLM이 아닌 잘림 요약을 생성합니다. 사용자의 대화는 절대 차단되지 않습니다. 응답은 약간 낮은 압축 품질로 계속되지만 지연은 없습니다.

### 회로 차단기

연속 요약 실패는 계층형 회로 차단기를 활성화합니다.

| Failure Type | Cooldown | Recovery |
|-------------|----------|----------|
| Transient (network/timeout) | 60 seconds | Half-open probe |
| Permanent (model error) | 10 minutes | Half-open probe |
| Auth failure | 30 minutes | Half-open probe |

휴지 기간 동안 모든 압축 요청은 결정적 대체를 사용합니다. 반개방형 프로브는 사용자 개입 없이 자동으로 복구를 테스트합니다.

### 진행 인식 시간 초과 가드

로컬 모델(Ollama, vLLM)은 요약하는 데 30~90초가 걸릴 수 있습니다. 듀얼 타임아웃 가드는 느린 모델이 절대 종료되지 않도록 보장하는 동시에 중단을 방지합니다.

| Guard | Threshold | Effect |
|-------|-----------|--------|
| **Inactivity timeout** | 90s without a new token | Raises `InactivityTimeoutError` → deterministic fallback |
| **Total wall-clock ceiling** | 600s absolute max | Raises `TotalCeilingTimeoutError` → deterministic fallback |
| **ProgressClock heartbeat** | Each streamed token resets idle timer | Distinguishes "slow but alive" from "completely hung" |

채팅별 잠금은 동시 압축 요청이 서로 짓밟히는 것을 방지합니다. 전체 압축 전 백업은 압축이 중단된 경우 100% 복구를 보장합니다.

### 압축 수명 주기 진단(UI)

압축이 3초 이상 걸리면 사용자에게 채팅 UI에 실시간 진행률 표시줄이 표시됩니다.

| Phase | What the user sees | When |
|-------|-------------------|------|
| (hidden) | Nothing — fast compression completes silently | <3s |
| `active` | "Compressing context (4.2s)" with elapsed counter | After 3s debounce |
| `timeout` | "Compression timed out, using fallback" (warning color) | Inactivity/ceiling exceeded |
| `circuit_open` | "Compression unavailable, using fallback" (warning color) | Circuit breaker tripped |
| `fallback` | "Compression degraded, using fast fallback" | LLM error |
| `completed` | "Context compressed successfully" (green) + tokens saved | Normal completion |

진행률 표시줄은 **업서트 로직**을 사용합니다. 하트비트 업데이트는 동일한 항목을 덮어쓰고(스태킹되지 않음) 3초 디바운스는 API 모델 사용자(1~2초 안에 압축)가 표시기를 전혀 볼 수 없도록 보장합니다.

### 대 경쟁사

| Feature | Myrm | Hermes | DeerFlow/CoPaw/OpenClaw |
|---------|------|--------|------------------------|
| Compression UI feedback | 5-phase lifecycle + elapsed_s + color-coded status | Plain text `status_callback` + default OFF (opt-in) | None |
| Debounce | 3s (fast compression = invisible) | None | N/A |
| Upsert logic | Single progress bar, updated in place | Text messages stack | N/A |
| Default state | Always ON | OFF (`silent-by-design`) | N/A |

**1,616개 테스트 검증**(SummarizeProcessor 49 + Middlewares 890 + Streaming 668 + Server Compact 9)은 시간 초과 보호, 수명 주기 이벤트 및 UI 통합 경로를 포괄합니다.

## 제로 구성 압축 및 모델 핫스위치

모델을 전환하거나 컨텍스트 매개변수를 조정하면 다음 메시지에 적용됩니다. 다시 시작하지 않고, `/reset`을 사용하지 않고, YAML을 편집하지 않습니다.

### 작동 방식

1. **DB 지원 구성**: 모든 모델/압축 설정은 GUI 설정을 통해 데이터베이스에 저장됩니다. 변경 사항은 즉시 유지됩니다.
2. **메시지별 지문**: `compute_execution_fingerprint()`은 30개 이상의 에이전트 매개변수(모델, 공급자, 엔진_매개변수, 프롬프트_모드, 기술 등)를 해시합니다. 모든 새 메시지는 현재 지문과 캐시된 지문을 비교합니다.
3. **자동 재구축**: 지문이 다른 경우 `ChatAgentExecutionCache`은 이전 에이전트 장치를 해체하고 사용자에게 투명하게 업데이트된 구성으로 새 에이전트 장치를 구축합니다.
4. **비례 임계값 자동 계산**: `ContextConfig(max_context_tokens=N)`는 모든 압축 임계값을 N:의 비율로 자동 계산합니다.
   - `compress_threshold` = N의 50%
   - `compress_force_threshold` = N의 70%
   - `summarize_trigger_threshold` = N의 90%
   - GPT-4o(128K)에서 Claude Sonnet(200K)으로 전환 → 모든 임계값이 자동으로 확장됩니다.
5. **자동 컨텍스트 창 검색**: `enrich_model_context_window()`은 500개 이상의 모델에 대해 LiteLLM 레지스트리에서 실제 `max_input_tokens`을 가져옵니다. 수동 `context_length` 구성이 필요하지 않습니다.
6. **자동 요약기 모델**: `summarizer_llm`의 기본값은 `lite_model`(더 저렴하고 빠름)이며 사용할 수 없는 경우 기본 모델로 자동 대체됩니다.
7. **회로 차단기 보호**: 요약 오류가 발생하면 반개방 프로브 복구 기능이 있는 회로 차단기가 트리거되며 계단식 오류는 발생하지 않습니다.

### 프론트엔드 시각화

- **컨텍스트 상태 링**(`ContextUsageIndicator`): 토큰 사용 비율, 상태 점(녹색/황색/빨간색), 원클릭 수동 압축 버튼 및 ≥75% 사용량의 자동 포크 CTA를 표시하는 실시간 SVG 링입니다.
- **Session Context Health Panel**(`SessionContextHealthPanel`): 압축 효율성, 정리 ROI, 캐시 적중률 및 적응형 백오프 상태를 다루는 20개 이상의 측정항목이 포함된 3카드 레이아웃입니다.

### 대 경쟁사

| Aspect | Hermes | Myrm |
|--------|--------|------|
| Config changes | Edit `config.yaml` → next message rebuilds agent | GUI Settings → DB → per-message fingerprint → auto rebuild |
| Compression params | 15+ manual YAML keys (`threshold`, `target_ratio`, `protect_last_n`, etc.) | Zero-config: proportional auto-calculation from `max_context_tokens` |
| Context window | Manual `model.context_length` in YAML | Auto-fetched from LiteLLM registry (500+ models) |
| Compression model | Manual `auxiliary.compression.model/provider` | Auto-selects `lite_model` with main-model fallback |
| Visibility | CLI text progress bar (60% info / 85% warning) | GUI Health Ring + 3-card analytics panel + fork guidance |
| Error handling | `hygiene_timeout_seconds` + cooldown | Circuit breaker with half-open auto-recovery |
