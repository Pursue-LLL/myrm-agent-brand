# Environment Variables

Configure your Myrm instance with environment variables. Copy `.env.example` to `.env` and customize.

## LLM Providers (WebUI, not environment variables)

Provider credentials are **not** environment variables. Add them in the WebUI under **Settings > Model Service**:
every provider keeps its own key, and Myrm stores it encrypted in the local data directory (`MYRM_DATA_DIR`,
`~/.myrm` by default). `.env` carries process and ops settings only.

> The `.env.example` shipped with the server states the same policy: only `[P]` process and `[O]` ops variables
> belong in `.env`; business capabilities (LLM, embedding, search, providers) live in WebUI Settings.

## Application

| Variable | Default | Description |
|----------|---------|-------------|
| `PORT` | `3000` | HTTP server port |
| `DATABASE_URL` | (empty) | Optional Apache AGE (PostgreSQL) graph store; empty keeps the graph in SQLite under the data directory |
| `MYRM_DATA_DIR` | `~/.myrm` | Root data directory (chat DB, vectors, memory, logs). Set before starting the service, then restart to apply |

> **Move the data directory:** on the desktop app, open Settings → System → Storage and click Change (guided move with space preflight, progress, verification and automatic rollback). For standalone WebUI/server, set `MYRM_DATA_DIR` to the new location and restart. Cloud hosting data lives on the managed persistent volume.

## Docker Compose

| Variable | Default | Description |
|----------|---------|-------------|
| `MYRM_BIND_HOST` | `127.0.0.1` | Host IP for port bindings. Set to `0.0.0.0` for LAN/remote access |
| `MYRM_PORT` | `25808` | Server API port |
| `FRONTEND_PORT` | `3000` | Frontend port |
| `MYRM_MEM_LIMIT` | `0` (unlimited) | Max memory for the Myrm container, e.g. `3g` |
| `MYRM_CPU_LIMIT` | `0` (unlimited) | Max CPUs for the Myrm container, e.g. `2.0` |
| `MYRM_WORKSPACE` | `./workspace` | Host directory mounted as the agent workspace |

## Security

| Variable | Default | Description |
|----------|---------|-------------|
| `JWT_SECRET` | (auto-generated) | JWT signing secret |
| `ENCRYPTION_KEY` | (auto-generated) | AES-256 encryption key |

## Observability & Telemetry

| Variable | Default | Description |
|----------|---------|-------------|
| `MYRM_LOG_FORMAT` | `text` | Log format: `text` or `json` (for ELK/Loki ingestion) |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | (empty) | Standard OpenTelemetry Collector endpoint (e.g. `http://localhost:4318` or `http://localhost:4317`) |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` | OTLP transport protocol: `http/protobuf` or `grpc`; when unset, an endpoint on port `4317` selects `grpc` |
| `OTEL_EXPORTER_OTLP_HEADERS` | (empty) | Auth headers as `key=value,key2=value2` (e.g. `Authorization=Bearer%20<token>`); never shown in the UI |
| `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` | `parentbased_always_on` | Standard sampling, e.g. `parentbased_traceidratio` with `0.1` keeps 10% of traces |
| `OTEL_SDK_DISABLED` | `false` | `true` switches all trace and metric export off |
| `OTEL_TRACES_EXPORTER` / `OTEL_METRICS_EXPORTER` | `otlp` | `none` switches that one signal off. A traces-only backend rejects metric batches (Jaeger answers `404` and the server logs each failed export); set `OTEL_METRICS_EXPORTER=none` for it |
| `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` | `false` | Opt-in: include prompt, reply and tool content in exported spans; off exports metadata only |
| `MYRM_LOCAL_TRACE_ONLY` | `0` | Air-gapped local mode: `1` enforces zero remote OTel export and keeps all traces purely local |
| `MYRM_CARDINALITY_FIREWALL` | `1` | Enforces metric label sanitization to prevent Prometheus high-cardinality OOM |

### Check that export works

Settings → Developer → OpenTelemetry export shows what each pipeline actually delivered, not what is configured. Traces read `Ready` until the first batch has been delivered or refused, then `Active` or `Failing` by the latest outcome. Metrics have their own state (`Off`, `Ready`, `Active`, `Failing`), because a backend can accept traces and refuse metrics. `GET /api/v1/system/telemetry-posture` returns the same measured fields (`status`, `metrics_status`, `exported_spans`, `failed_batches`, `last_success_at`, `last_failure_at`), and `otlp_connected` in the `gatewayRuntime` block of `GET /api/v1/health/liveness` is derived from them: it is `true` only while the latest export was accepted.

On a platform-managed (cloud-hosted) instance the collector belongs to the operator, so the card is hidden and the API withholds the collector address.

### How a request's trace lines up

For one HTTP request the same 32-hex id is the `X-Trace-Id` response header, the `error.trace_id` of an error response, the id in the server log lines and the trace id of the exported spans, so an id quoted from an error message finds its trace directly. A caller that sends a valid `X-Trace-Id` (32 hex characters, not all zero) or W3C `traceparent` keeps its own id (`X-Trace-Id` wins); any other value is replaced by a fresh one.

The spans are agent runs, model calls, tool calls and, for chat channels, one `stream_reply` trace per streamed reply. HTTP requests produce no spans of their own, since health probes would only add noise. The `OTEL_*` variables are read by the server only: programs the agent runs (terminal commands, scripts, background processes, the browser) do not inherit them, and one that needs OpenTelemetry sets its own on its command line.
