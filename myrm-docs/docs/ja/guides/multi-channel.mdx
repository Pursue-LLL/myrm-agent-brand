# マルチチャネル統合

あらゆるメッセージングプラットフォームからエージェントにアクセス——35+チャネル、自動フォーマット適応付き。

## 対応チャネル

| カテゴリ | チャネル | 数 |
|----------|----------|-------|
| IM | Discord、Slack、Telegram、WhatsApp、Signal、Line、Matrix、Mattermost、IRC | 9 |
| 中国エコシステム | WeChat、WeCom、WeCom AIBot、DingTalk、Feishu、QQ、OneBot、WeChat Official | 8 |
| 開発者 | GitHub（Webhook＋PRコメント） | 1 |
| 企業 | Microsoft Teams、Google Chat | 2 |
| 音声 | Discord Voice（DAVE E2E暗号化付き） | 1 |
| その他 | Email、SMS、iMessage、Webhook、Zalo | 5 |

## iMessage深層統合

[BlueBubbles](https://bluebubbles.app/)（無料・オープンソースのmacOSリレー）経由でiMessage接続。MyrmはBlueBubbles Private APIを完全実装し、ネイティブiMessage体験を提供します：

| 機能 | 説明 |
|---------|-------------|
| 引用返信 | エージェント返答が元メッセージを可視引用バブル付きで参照 |
| 既読 | 受信メッセージを「既読」化——エージェントが受信したとユーザーが分かる |
| Tapbackリアクション | ネイティブiMessage tapbackでリアクション可（ハート・親指上下・笑・感嘆・疑問） |
| 入力中表示 | エージェント処理中に「入力中…」バブル表示（55秒自動更新キープアライブ） |
| Webhook自動登録 | 一度設定——起動時登録・停止時解除。手動BlueBubbles設定不要 |
| メディア添付 | 画像・動画・音声・文書・連絡先カード（vCard）完全対応 |
| グループチャット | グループ会話対応（グループごとコンテキスト＋送信者識別） |

### セットアップ

1. iMessage有効なmacOSマシンに[BlueBubbles](https://bluebubbles.app/)をインストール
2. GUIで**設定 > チャネル > iMessage**へ
3. BlueBubblesの**API URL**と**パスワード**を入力
4. 任意で**Webhook URL**——エージェントが接続時に自動登録
5. 引用返信・既読・入力中表示のためにBlueBubblesで**Private API**を有効化

### グレースフル劣化

BlueBubbles Private APIやヘルパープロセスが使えない場合、それを要する機能（入力中表示・既読・引用返信）は黙ってスキップ——無駄なネットワーク要求なし、ログにエラーなし。基本メッセージは中断なく動作継続。

## セットアップ

GUIの**設定 > チャネル**でプラットフォームに接続。各チャネルに接続状態インジケータ付き設定パネルがあります。

API認証情報を要するチャネル（DingTalk・Slack・Discord・WeCom等）では、設定フォーム下に**開発者ポータルリンク**表示——クリックで各プラットフォームの開発者コンソールへ直行し、bot/appを作って認証情報を取得。12チャネルが直リンク、4チャネルが文章ガイダンス。

### Public Ingressガイダンス

一部チャネルはプラットフォームが公開URLへwebhookコールバックを**push**して受信——LINE・Teams・WeChat Official・Zalo・SMS（Twilio）・GitHubは到達可能な公開アドレスが必要。他は**outbound**接続——Feishu WebSocket・Telegramロングポーリング・Email IMAP・IRC/Matrix——公開アドレス不要。

Myrmは設定**前に**どちらかを教えます：

| 機能 | 内容 |
|-----------|--------------|
| 自動モード検知 | 設定→チャネル頁にチャネルごと**inbound / outboundバッジ**表示。全組込チャネルのトランスポートプロファイルからサーバー側算出 |
| 設定時警告 | Public Ingress URLなしでinboundチャネルを設定すると**警告**＋設定→システム→Public Ingressへのワンクリック修復リンク |
| トンネルガイド | 公開IPなし？[トンネルガイド](/docs/guides/tunnel)に従いcpolar / NATAPP / frpでローカルエージェントを公開 |

定番の「webhookが届かない」デバッグ地獄とおさらば——接続前に公開アドレス要否と設定場所が分かります。

> **正直境界**：Ingressガイダンスはチャネルごとのトランスポート分類であり、ライブ接続試験ではありません。webhook到達はトンネル/プロキシがプラットフォームから到達可能であることに依存します。

### WeChat（iLink経由）

個人WeChatアカウントを1分以内にQRログイン接続：

1. GUIで**設定 > チャネル > WeChat**へ
2. **スキャンして接続**をクリック——QRダイアログ出現
3. スマホのWeChatでQRをスキャン
4. スマホで確認——ダイアログがリアルタイム更新（SSEストリーミング）
5. 完了——WeChat接続済み

ログインフローはリアルタイム状態更新付き：QR生成→待スキャン→検証中→接続済み。QR失効時は**再試行**で新規発行。

**入力中表示の信頼性**：iLink入力チケットは600秒で失効。長時間エージェントタスク（10分超）では失効前に先回り更新（540秒閾値＋60秒安全バッファ、単調時計でドリフト安全）。「入力中…」がエージェント完了時に必ず消えます——凍結入力中なし。

### WeChat Officialアカウント（下書き発行）

**購読/サービスアカウント**用（個人WeChatではありません）。**AppID＋AppSecret**を設定し、WebUI確認後に整形HTMLを**下書き箱**へpush。

完全ガイド：[WeChat Officialアカウント発行](/docs/guides/wechat-official-publishing)。

1. **設定 → チャネル → WeChat Official** — AppID・AppSecret・IPホワイトリスト・接続試験
2. **wechat-article-formatter**でvault Markdownを整形→`.wechat.html` artifact
3. chat でプレビュー→**WeChat下書きへPush**（題＋表紙。先頭 inline 画像を自動推奨）
4. [mp.weixin.qq.com](https://mp.weixin.qq.com/)の下書き箱から手動発行

<Note>
下書きpushは**HITLのみ**——Agent下書きツールなし（Prompt Cacheフレンドリー、誤爆なし）。
</Note>

### WhatsApp（Baileys経由）

1. GUIで**設定 > チャネル > WhatsApp**へ
2. **スキャンして接続**をクリック——WeChatと同じQRダイアログ
3. スマホのWhatsApp → **リンク済みデバイス** → QRスキャン
4. 自動接続確立

WeChatもWhatsAppも同じ`AsyncLoginProtocol`——チャネルをまたいで一貫UX。

### Email（IMAP＋SMTP）

1. **設定 > チャネル > Email**を開く
2. IMAP（受信）とSMTP（送信）のサーバー・ポート・認証情報を設定
3. 保存——ポーリング自動開始

**賢い転送メール解析**：メールをエージェントに転送すると、あなたの指示と元メール本文を自動分離。

- Gmail・Outlook・QQ Mail・163 Mail・Foxmail等主要クライアント対応
- 三層検出：件名前置（Fwd:/FW:/转发:/轉發:）→本文区切り→MIME添付
- 転送時に「expense this」「translate to English」と書くだけ——エージェントは指示と元メール全文の両方を見て正確に実行
- フルCJKメールクライアント対応、適応文字コード復号（gb2312/GBK/UTF-8）

**賢いHTMLクリーニング**：メールがHTMLのみの場合（Amazon注文・Jira通知・Outlookリッチテキスト等）、自動でクリーンMarkdownに変換——表・リンク・箇条を保持しつつ容量65–74%削減（実測）。エージェント理解が速く正確に。

**マルチエージェントメール振分**：複数Agent設定時はメール本文先頭のスラッシュコマンドで宛先エージェント指定：

- `/coder review this PR` → "coder"エージェントへ
- `/accountant expense this` → "accountant"エージェントへ
- コマンドなし → 既定エージェントへ

### Telegram

Telegram接続は二経路——状況で選択：

**経路A：オンボーディングウィザード（初回ユーザー推奨）**

初回セットアップウィザードで、モデルと振分設定の後に**Telegramパーソナルアシスタント**ステップ出現：

1. **Bot Token**を貼付け（[@BotFather](https://t.me/BotFather)で取得）
2. 任意で**Webhook URL**（公開ドメイン背後のVPS/クラウドデプロイのみ要）
3. 任意でアシスタント名（既定`Myrm Assistant`）
4. **有効化**をクリック——トークン検証・認証情報書込・DMポリシー"open"設定・既定Agent束縛を原子的に実行

どこか失敗したら全変更を自動ロールバック——中途半端な状態なし。並行送信も優雅に処理：他要求が進行中なら自動再試行し、生エラーでなく親切メッセージ表示。

**経路B：設定頁（後からTelegram追加）**

1. **設定 > チャネル > Telegram**へ
2. **Bot Token**と任意の**Webhook URL**を入力
3. 保存——bot接続・受信開始

**Webhook vs ポーリング**：Webhook URLなしはロングポーリング（ローカル/デスクトップ向け）。Webhook URLありはTelegramがサーバーへpush（botがインターネット到達必須のVPS/クラウド向け）。

**リッチメッセージ描画**：TelegramはBot API 10.1ネイティブリッチメッセージ対応——表・LaTeX数式・入れ子箇条がネイティブ描画。詳細は[Telegramリッチメッセージ](#telegram-rich-message-bot-api-101)。

### iMessage（BlueBubbles経由）

iPhone・iPad・Mac、そして**アプリ不要のApple Watch手首操作**まで、エージェントをAppleエコシステムに接続。

1. **設定 → チャネル → iMessage**
2. BlueBubblesサーバーの**API URL**（例`http://127.0.0.1:1234`）と**パスワード**を入力
3. webhook URLを設定して保存
4. （任意）「メンション pattern」下でグループ wake-word 正規表現を設定（既定：`^@?(?:Myrm|myrm|小助手|助手)\b`）

**要点ハイライト**：
- **Apple Watch手首到達**：サードパーティWatchアプリ不要。ネイティブメッセージアプリでエージェントに text し、高リスクツール実行（HITL）をTapback 👍リアクションで承認
- **グループ wake-word と prefix 清掃**：グループ chat でwake-wordを自動照合・句読点ごと除去。**100% Prompt Cache保持**を保証
- **ヘルス診断とヘルパー状態**：BlueBubbles Private APIとヘルパー接続のリアルタイム診断インジケータ

### Slack

**設定 → チャネル → Slack**で接続——Bot Tokenを貼付け（Socket Mode用App Tokenは必要時）、接続試験、完了。CLIもenvファイル編集も不要。

**Slackで得るもの：**

| 利点 | 意味 |
|---------|----------------------|
| **プロ級見た目の返答** | エージェントMarkdownをSlack mrkdwnへ自動変換——太字・リンク・取消線が正しく描画。CJK文字と書式マーカー隣接も対応 |
| **ライブ streaming** | 返答を typing 表示付きインプレース更新——断片洪水なし |
| **対話承認** | Block Kitカードの承認/拒否ボタン。スレッド対応コンテキストで長期タスクも整理 |
| **GUI設定** | 接続試験・スレッド選択・SaaS ingressガイダンス付き完全設定パネル |

> **正直境界**：Hermesには超長Markdown（表・見出し）をネイティブSlackレイアウト化する任意リッチブロックモードがあります。Myrmは今、確実なmrkdwn＋対話ボタンに集中——日常チーム chat に十分。複雑な表レイアウトは等幅フォールバックの場合あり。

### SMS（Twilio）

1. **設定 > チャネル > SMS**を開く
2. Twilioの**Account SID**・**Auth Token**・**電話番号**（E.164形式、例`+15551234567`）を入力
3. 自動生成**Webhook URL**をコピーしてTwilioコンソール > 電話番号 > メッセージングwebhookへ貼付け
4. **接続試験**で検証

- 双方向：任意電話からSMS受信→エージェント処理→SMS返信
- 長文は自然境界で自動分割（1セグメント最大1600文字）
- Twilio署名検証で正規メッセージのみ処理

## メッセージ種別

全チャネル対応：

- プラットフォーム適応書式のテキストメッセージ
- 画像/文書/音声/動画添付（`MediaType` enum）
- 自動種別検出のファイル upload

## 双方向ファイル転送

エージェント生成ファイルは自動でIMへpush——手動ダウンロード不要。

### Inbound（ユーザー → エージェント）

IMで文書（PDF・Excel・Word等）をエージェントに送ると、内容を自動抽出してLLMコンテキストへ注入。ファイル読みツール呼び出しなしでエージェント即理解。

### Outbound（エージェント → ユーザー）

エージェント作成ファイル（図・報告・表・コンパイル文書）は chat 内メディア添付で自動配送。対応artifact種はコード実行・ファイル書込・文書生成の全生成物。

| 機能 | 詳細 |
|---------|---------|
| サイズ上限 | 1ファイル5 MB（超過は優雅 skip） |
| 失敗処理 | 自動再試行＋メディア剥離フォールバック——文面は決して欠損しない |
| 対応種別 | IMAGE・DOCUMENT・AUDIO・VIDEO（ファイル名から自動検出） |
| 複数ファイル | 生成物は全て個別添付で配送 |

### Artifact深リンク

対話artifact（HTML頁・PDF・文書）は、生ファイルでなく chat 内にクリック可**深リンクボタン**を自動生成。タップでユーザーブラウザに直接開く——ダウンロード不要。

| 機能 | 詳細 |
|---------|---------|
| 発火 | 共有可artifact種（HTML・PDF・Document）に自動 |
| 安全 | HMAC署名・期限付き・読取専用共有トークン |
| 複数artifact | 命名ボタンずつ（例「💻 dashboard.html」） |
| 冗長除去 | 深リンクあり時は生ファイル添付を除去 |
| 安全劣化 | 公開URLなし・DB異常・トークン失敗時は生ファイルにフォールバック |
| i18n | ボタン標記を地域化（英語 / 中国語） |

## チャネル対応出力適応

Myrmは**三層**架构で全プラットフォームに出力を清潔・正書式に：

### Outboundノイズ濾過

チャネルごとに`RenderStyle`設定がユーザー可視内容を制御：

| 制御 | 選択肢 | 既定 |
|---------|---------|---------|
| `reasoning_display` | OFF / COLLAPSED / INLINE | OFF（WeChat・WeCom・WhatsApp）or COLLAPSED（Telegram） |
| `tool_summary_display` | OFF / COMPACT / DETAILED | OFF（WeChat・WeCom・WhatsApp）or COMPACT（Feishu・DingTalk） |

既定でIMユーザーが受け取るのは**進捗ラベル・最終結果・判断プロンプト**のみ——ツール呼び出し引数・推論トークン・思考タグなし。`strip_thinking_tags()`関数が漏出LLM思考ブロックを除去する追加安全網。

進捗ラベルは**入力サマリ**付きで、エージェント動作が正確に見えます：

- `🔍 Searching: AI coding tools 2025`（「Searching the web...」だけでなく）
- `📄 Reading: config/settings.yaml`（「Reading file...」だけでなく）
- `⏳ **notion_query** — Search meeting notes`（カスタムMCPツールも自動対応）

全ツール対応——登録ツールは固有動作表示、未登録ツール（設定した任意MCPサーバー含む）は入力抽出付き汎用フォールバック。更新は抑制（最小2秒間隔）でAPI制限回避。

### 事前ガイダンス（channel_output_hints）

エージェント初期化時にチャネル固有書式ヒントをシステムプロンプトへ注入。LLMが生成**前に**プラットフォーム対応を知ります：

- **Telegram**：Bot API 10.1リッチメッセージで表・LaTeX・入れ子箇条がネイティブ描画。ヒントはRich不可時のみ有効
- **WhatsApp**：「Markdownは描画されない——プレーンテキストのみ」
- **Discord**：「2000文字超メッセージは自動分割」
- **音声**：「対面会話のように話す」

28チャネルヒントが事前設定・KV-Cache安全（初期化時一度注入）。

### IM振舞ペルソナ（自動注入）

制限IMチャネル（メッセージ編集不可・Markdown非対応）には振舞方策を自動注入：

- **簡潔 chat 文体**：教科書でなく chat 会話のように返答
- **長文 → ファイル＋要約**：約200文字超は workspace ファイルに書出し。IM返答は一文要約＋Artifact深リンクのみ
- **集中確認**：ユーザー意図不明時は最大1–2の要点質問

自動発火チャネル：WeChat iLink・WeChat Official・Signal・iMessage・LINE・SMS・OneBot（QQ）・IRC・Zalo・音声（計10）。

ゼロ設定で自動——`ChannelCapabilities`から検出。Markdownや編集対応チャネル（Telegram・Discord・Slack等）は不変。

### 事後書式劣化（renderer）

LLMがヒント無視でも描画パイプラインが書式劣化を適用：

- `supports_tables=false` → Markdown表を箇条に変換
- `supports_latex=false` → LaTeX数式を剥いで平文に
- IMチャネルでHTML/SVGコードブロックを短プレースホルダに置換
- 孤児引用マーカーを出典なし時に自動清掃

### メッセージごとコスト表示

`enableCostEstimation`有効時（既定true）、IMチャネルの各エージェント返答にコストフッタ付き（使用モデル・トークン数・推定額）：

```
💰 claude-sonnet-4-20250514 | 2.5k tokens | ~$0.0035
```

- **ゼロコスト返答は非表示** — キャッシュや無料モデル返答にフッタなし
- **絵文字トグル** — `💰`接頭をユーザー設定で無効化可（データは保持）
- **Feishuカード** — コストはタイムスタンプ横のネイティブ`note`要素に
- **精度** — コストは常時小数4桁で正確追跡

追加設定なしで自動動作。コストデータは streaming 中 harness `token_usage`イベントから抽出。

### 賢いメッセージ分割

長文は自然境界で自動分割：

- コードフェンス状態機械でチャンクをまたいでコードブロックを正しく閉開
- 空白・句読境界の知的行分割
- 意味保持の設定可オーバーフロー許容
- チャネルごと長さ上限（例Discord 2000文字、Telegram 4096 HTML / 32000リッチメッセージ）

### Telegramリッチメッセージ（Bot API 10.1）

Telegramチャネルは3層フォールバックのネイティブリッチメッセージ描画対応：

1. **リッチメッセージ** — 表・LaTeX数式・入れ子箇条がネイティブ描画（32KB上限）
2. **HTML** — 自動変換＋ASCII等幅表劣化（4096 UTF-16上限）
3. **プレーンテキスト** — HTML解析失敗時の最終手段

streaming は**ちらつきなしドラフトプレビュー**（`sendRichMessageDraft` → `sendMessageDraft` → `editMessageText`）。20文字最小閾で初回トークンちらつきを抑制。CJKは完全リッチ書式——劣化も回避策もなし。

## グループチャット機能

### AllowPolicy

三定型ポリシーがグループ chat のエージェント応答を制御：

| ポリシー | DM | グループ |
|--------|-----|-------|
| OPEN | 全許可 | 全許可（メンション不要） |
| SELECTIVE | 全許可 | メンション必須 |
| STRICT | メンション必須 | メンション必須 |

### GroupTriggerMode

グループ chat のエージェント発火を細粒度制御：

| モード | 動作 |
|------|----------|
| ALL | グループ内全メッセージがエージェント発火 |
| MENTION_ONLY | @メンション時のみ応答 |
| PREFIX | 設定 prefix 始まりに応答（prefix自動除去） |

### トピック束縛

三層粒度で異なるエージェントを異なる会話範囲に束縛：

- **スレッド層**：特定トピック/スレッドに束縛
- **Chat 層**：特定グループ/会話に束縛
- **チャネル層**：チャネル源全体に束縛

探索順はスレッド→Chat→チャネル、優雅に既定エージェントへフォールバック。

### トピック Workspace 束縛（Vault / プロジェクト）

各IMトピックを本物 workspace に束縛。リモートメッセージが空JIT sandboxに落ちません。

| 方法 | 手順 |
|--------|-----|
| **GUI** | **設定 → チャネル振分** → トピックごと**プロジェクト**ドロップダウン |
| **IM** | `/bind workspace=project:<uuid>` or `/bind workspace=/path/to/vault` |
| **複合** | `/bind agent=my-agent workspace=project:<uuid>` |

各Agent実行前にトピック束縛を chat SSOT（`project_id` or `workspace_dir`）へ同期。WebUIセッションと同じ`resolve_effective_chat_workspace`鎖。束縛解除は両欄クリア。プロジェクトやパスが使えなければ、空sandbox黙用でなく大声で失敗。

**正直制限：** IM `/status`は依然`project:uuid`表示（フレンドリ名でない）。GUIパス選択器なし——GUIユーザーはプロジェクト束縛、パス束縛はIM優先。

**試験範囲：** サーバーpytest 9件（同期・topic_config検証・解除クリア・effective_workspace鎖）。フロントエンド標記ヘルパー：vitest 3件。

**vs OpenClaw：** OpenClawはAgent設定層で`workspaceDir`束縛——Agentごと1 workspace。Myrmはトピック粒度束縛なので、同一Agentが異なるTelegramスレッドに異なるvaultを向けられます。

### Obsidian Vault書込忠実度

トピックをObsidian vaultに束縛すると、エージェント編集は**本物vaultファイル**へ（コピーでない）。Myrmはコードレベル2保護を追加：

1. **Frontmatter保持** — LLMが本文編集中に`---` YAMLブロックを落としても、書込ガードが保存前に編集前frontmatterを再注入（`date:`・`tags:`・Dataview欄が intact）
2. **vaultノートにprettierなし** — FormatObserverが`.obsidian/` vault根下`.md`を skip。自動整形のメタデータ剥離なし

**正直制限：** ブロック単位再注入のみ（欄単位マージでない）。Wikilink完全性は`obsidian-notes`スキル依存——vault全域backlink走査は未。

**試験：** pytest 44件（Jul 2026）：harnessガード＋サーバーパーサ＋サービス統合＋format observer。

### スレッド追従

スレッド内でエージェント応答後、そのスレッドに**GroupFollowUpTracker**発火（TTL：10分）。 window 内は同スレッド後続メッセージに@メンション不要——エージェント自動継続。人間同様。

追従停止はスレッドで`/mute`・`/shutup`・`闭嘴`・`别吵`。エージェント即停止。再開は単に@メンション。

### ゲストメンション

エージェント未有効グループでも、ゲストモード有効時は@メンションでワンショット応答可（one-shot）。ホワイトリスト追加なしのアドホックAI支援。

### 正確Bot ID照合

全チャネルプロバイダが正確bot身元照合——Telegramは`bot_username`、Feishuは`bot_open_id`、Teamsは`app_id`、WhatsAppは`mentionedJids`検査。@メンションは常時正確botへ振分。35+チャネルで誤発火ゼロ。

### GroupContextBuffer

グループ chat の非発火メッセージはグループごとリングバッファに蓄積。発火メッセージ到達時（例@agent）にバッファを流してコンテキスト注入——グループ議論の会話認識をエージェントに。

### SessionGate

同一会話の連射メッセージはデバウンス（既定300ms window）統合1要求に。重複処理防止。

## 決定論LLM前処理

全 inbound メッセージはモデル到達前に5層ゼロLLMコスト処理を通過。常用操作はトークン消費ゼロでミリ秒応答。

| 層 | 動作 | 遅延 |
|-------|-------------|---------|
| **メッセージ重複排除** | TTL重複排除（`channel:message_id`）でWebhook再試行の重複処理を防止 | <0.1ms |
| **スラッシュコマンド** | 21系コマンド＋動的スキル束縛＋エージェント振分——O(1)登録簿探索 | <0.1ms |
| **リスク検知** | コンパイル正規表現エンジンが機密内容をブロック/警告。ReDoS安全＋監査証跡 | <1ms |
| **FAQ意味キャッシュ** | embedding類似＋score/gap二重検証——キャッシュ hit はテンプレ回答即返（LLM比40–100倍速） | 5–20ms |
| **ポリシー＋セッションゲート** | DM/グループポリシー執行、メッセージデバウンス（300ms）、統合、並行制御 | <1ms |

### ユーザー視点の意味

- **よくある質問は即答** — FAQ hit はLLMを skip。時間も金も節約
- **機密内容は自動ブロック** — 手動モデレーションなしでコンプラ対応
- **高速コマンド待機ゼロ** — `/stop`・`/new`・`/status`即実行
- **連射メッセージ優雅処理** — バーストは統合、冗長処理なし
- **トークン無駄なし** — 真にAI推論を要するメッセージのみモデル到達

## エージェント発信通知

エージェントが設定チャネルへ能動push通知——手動ポーリング不要。

### 仕組み

1. **エージェント設定 → 通知チャネル**で**稼働中**統合からチャネル選択（動的リスト・人間可読名——新チャネルはフロントリリースなしで出現）。ペア済み連絡先から宛先選択（or ID手入力）
2. エージェントが通知要時（タスク完了・異常検知・定期報告 ready）に`channel_notify_tool`呼出
3. 任意でファイル・画像添付——ローカルパスとURLは自動解決＋正しいメディア種別検出
4. 配送は`send_tracked`で同期成否結果（重要チャネルメッセージと同再試行策）。fire-and-forget置き去りなし

> **通知配送との違い**：**エージェント設定 → 通知チャネル**は`channel_notify_tool`のみホワイトリスト。**設定 → 通知配送**は**系イベント**（OAuth・予算・ペアリング・チャネルヘルス）を振分。互換なし。

### セキュリティ

| 層 | 保護 |
|-------|-----------|
| ホワイトリスト | ユーザー設定宛先のみ到達。未設定時0トークン overhead（オプトイン mount） |
| 読取専用ガード | 送信通知ツールは読取専用安全プリセットで厳格拒否（`is_readonly=True`）。 egress データ漏洩防止 |
| 流量制限 | セッションごと上限で通知スパム防止（既定：1セッション10） |
| 内容上限 | `max_body_length`（4000文字）超メッセージは自動切詰 |
| 添付 | ローカルパスはエージェント workspace 内必須（`declared_allowed_roots`）＋`os.path.exists`/`os.path.isfile`検証。URLファイル名は安全解析（クエリ対応） |
| 監査証跡 | 使用通知宛先は全てセッション状態に記録 |
| サブエージェント隔離 | サブエージェントは既定で`channel_notify_tool`不可（harness L1 blocklist） |
| 失敗可視 | 同期配送失敗はDLQ入り＋WebUIトースト発火（presync重複排除。再起動またぎ非永続） |
| 層 | サーバー`outbound_notify/`（業務層、harness kernelでない）。ChannelGatewayと同居 |

> **試験範囲（2026-09-03）**：**自動試験171+（読取専用モードガード・sandboxファイル検証・DLQ/トースト鎖・サブエージェント隔離・添付パス sandbox 含む）＆ライブChrome E2E** passing。

### 例シナリオ

- 午前3時予約タスク完了→エージェントが概要＋報告PDFをTelegramへ
- 長時間コード分析完了→結果＋生成図をSlackチャネルへpush
- 監視データ異常検知→ダッシュボードスクショ付き警告を所定宛先へ

## Web Push（オフライン通知）

ブラウザを閉じても重要警告を受信——ネイティブアプリ不要。

PWA終了・バックグラウンド時もサーバーがW3C Web Push標準（VAPID）でpush通知。IM未設定時やブラウザネイティブ警告が欲しい場合をカバー。

### 対応イベント

| イベント | 例 |
|-------|---------|
| 承認要求 | 機密操作の実行にエージェントが許可要 |
| 目標完了 | バックグラウンドタスク正常終了 |
| 目標失敗 | タスクが回復不能異常に遭遇 |
| 目標検証 | 結果が査読 ready |
| ヘルス警告 | 系が service 断を検知 |
| 予算警告 | 使用量が設定上限接近 |
| バックグラウンドタスク完了 | 長時間タスク終了 |
| 系通知 | 安全イベント・ペアリング要求・OAuthコールバック |

### セットアップ

1. **設定 > システム > Push通知**へ
2. **有効化**トグル——ブラウザが通知許可を要求
3. 完了。ブラウザタブを閉じても通知到達

**試験**ボタンで即配送検証可。

### プラットフォーム注記

| プラットフォーム | 対応 |
|----------|---------|
| デスクトップブラウザ（Chrome・Firefox・Edge） | ✅ 完全対応 |
| Android（Chrome・Firefox） | ✅ 完全対応 |
| iOS / iPadOS（Safari 16.4+） | ✅ 「ホーム画面に追加」（PWAモード）要 |
| Tauriデスクトップアプリ | N/A — ネイティブOS通知を使用 |

iOSではPWA standalone動作中かをカードが自動検知し、必要時は導入ガイド表示。

### 安全と保守

- **VAPID鍵自動生成** — サーバーが初回起動時に生成永続。ゼロ設定
- **失効購読清掃** — push失敗（410/404）で古い購読を自動除去
- **サードパーティなし** — ブラウザベンダー endpoint へ直送（Google FCM・Apple APNs・Mozilla autopush）
- **Tauri対応** — ネイティブ通知が動くデスクトップapp build では設定カード非表示

### ワンクリック承認深リンク

push通知タップで正確 chat と**承認ドロワー**を開く——ホーム頁でなく。

- **承認要求**は`/{chat_id}?approval={id}`へ。WebUIが全体承認ドロワーを開き、クリーンURL用にクエリ除去
- **Service Worker振分**は同一起源パスを消毒。 chat タブ既開時はfocusのみでなく`navigate()`呼出——開タブの新規承認もドロワーが開く（OpenClawのSWはpathname比較のみで取逃し）
- **Chrome MCP E2E検証済み** — hot tab＋コールドスタート深リンク経路（2026-07）

## バックグラウンドタスク自動返信

任意IMチャネルで`/btw`開始したバックグラウンドタスクの結果は、完了時に自動で元会話へpush返信：

- **スレッド精密配送** — 返答はタスク開始スレッドに着地
- **地域化通知** — 言語設定を尊重（英語・中国語他）
- **失敗警告** — 失敗時は沈黙でなく誤り概要
- **確実配送** — 全チャネルメッセージと同再試行基盤
- **非破壊** — 通知設定と独立。これは直接返答で放送でない

Discordでタスク開始、他事して戻ると結果がスレッド待機。

## 目標完了自動返信

任意IMチャネルで`/goal set`開始した目標の完了結果は、完了時に自動で元会話へpush返信：

- **スレッド精密配送** — 開始スレッドに着地
- **地域化通知** — 目標作成時の使用言語を尊重（英語・中国語・日本語・繁体中国語）
- **深リンクボタン** — 「ブラウザで続ける」でWebUIに目標詳細＋実行概要を全表示
- **成否両対応** — 完了も失敗も通知発火
- **一貫基盤** — `/btw`バックグラウンドタスク通知と同配送管

Telegramで目標開始、アプリを閉じ、数時間後に構造化結果——ワンクリックでブラウザ全詳細へ。

## 長時間ハートビート（インプレース編集）

エージェントが長時間複雑タスクで無出力のとき、停滞誤認防止のライブハートビートを自動送信——複数通知で chat を洪水にしない。

### 仕組み

1. 並行バックグラウンド監視が最終活動（メッセージ送信・進捗更新等）からの経過を追跡
2. 2分沈黙でハートビートを元IMチャネルへ送信
3. 以降ハートビートは**同メッセージをインプレース編集**（経過・歩数・段階を更新）——新規メッセージなし
4. メッセージ編集非対応チャネルは1通のみ送信（スパムなし）
5. 1タスク最大3ハートビート周期
6. NORMAL優先度——ハートビートは静粛到達。スマホpush発火なし

### 例メッセージ

> ⏳ Working — 3 min (12 steps, data analysis)

進捗に応じてインプレース更新：

> ⏳ Working — 5 min (18 steps, code generation)

### 賢い沈黙検知

単純間隔タイマーと違い、監視は**エージェント出力でリセット**。1分時点で進捗更新があれば2分沈黙 window はそこから再起動。活発通信中の不要リマインドなし。

### チャネル対応適応

ハートビートはチャネルのメッセージ編集対応を自動検知（`ChannelCapabilities.edit`）。Telegram・Discordはインプレース編集対応。非対応チャネルは1通ハートビートのみ送信し、スパム回避の更新なし。

編集失敗時（例メッセージ古すぎ）は優雅に新規送信へフォールバック。

### 詳細

| 項目 | 動作 |
|--------|----------|
| 沈黙閾 | 120秒（`_SILENCE_REASSURANCE_THRESHOLD`で設定可） |
| 最大ハートビート | 1タスク3（`_MAX_REASSURANCE_COUNT`で設定可） |
| 更新式 | インプレース編集（編集非対応は単発送信へフォールバック） |
| 優先度 | NORMAL — 静粛配送、push通知なし |
| 言語 | 完全国際化（英語・簡体中国語・繁体中国語・日本語——`.ftl`で拡張可） |
| 入力中表示 | 並行動作——沈黙 window 中も「入力中…」継続 |
| Prompt cache | ゼロ影響——ハートビートは outbound のみ。系プロンプト不変 |
| 異常処理 | 送信/編集失敗は黙ってログ。主タスク不中断 |

## chat 内エージェント切替

任意IMチャネル内で設定エージェントを直接切替——Web UIを開く必要も設定ファイル編集も不要。

### Telegram（`/agent`コマンド）

1. 任意 chat で`/agent`送信
2. InlineKeyboardに全エージェント一覧——現束縛エージェントに check 表示
3. 宛先タップ——ピッカー文が確定文に置換（「Switched to: AgentName」）
4. 以降同トピックの全メッセージが新エージェントへ（独立系プロンプト・モデル・ツール・メモリ）

### クイックスイッチコマンド

設定に`command_bindings`を持つエージェントは短縮コマンドを登録（例`/claude`・`/gpt`）。

**二重振分：**

- `/cc fix this bug` — **ワンショット振分**：本メッセージはClaudeエージェント処理、束縛不変（次メッセージは前エージェントへ）
- `/cc`（引数なし） — **永続束縛**：既定エージェントをClaudeに切替（以降全メッセージ）

一時的他エージェント要時の往復摩擦を解消。

### トピック束縛粒度

エージェント束縛は**三層解決**階層に従う：

| 層 | 範囲 | 例 |
|-------|---------|---------|
| スレッド | グループ内1返信スレッド | スレッドごとに異なるエージェント |
| Chat | DM会話 or グループ全体 | 大半の用途の既定 |
| チャネル | 1チャネル源の全会話 | スレッド/chat束縛なし時のフォールバック |

### i18n対応

ピッカーと確定文は完全国際化。エージェントがユーザー言語設定を自動解決（現状英語と中国語、`.ftl`翻訳ファイルで拡張可）。

## cross-device タスク同期

全バックグラウンドタスクはサーバー側保管。任意接続クライアントから到達——デスクトップapp・Web UI・モバイルブラウザ：

- **唯一真実源** — タスク状態はサーバーKanban系に存在。単一デバイスにない
- **全所リアルタイム更新** — SSEイベントが状態変化（完了・失敗・進捗）を全接続クライアントへ同時push
- **一貫UI** — デスクトップ（Tauri）は同一Web UIフロントエンドを内包。全表面で体験同一
- **IMチャネル統合** — BtwTaskNotifierがUI更新と並行でIMチャネルへ結果push
- **IM Kanban管理** — Telegram・Discord・Slack等で直接`/kanban`（or `/kb`）。 chat を離れずタスク作成・一覧・編集・完了・ block ・アーカイブ。ゼロLLMコスト——コマンドはAgent管をバイパス

デスクトップでタスク開始、スマホで進捗確認、Telegramで`/kanban`管理、Slackで完了通知——設定なし全自動。

## cross-platform 引継ぎ

会話をプラットフォーム間でコンテキスト欠損なし移送。

**二入口：**
- **Web UI** — サイドバー任意会話を右クリック→「転送先…」→ダイアログが全接続チャネルを自動検出（アイコン＋状態）→選択してワンクリック転送
- **IMコマンド** — 任意IMチャネルで`/handoff <target_channel>`入力（Telegram・Discord・Slack等）

**仕組み：** 引継ぎはセッション鍵を宛先チャネルへ単一原子DB更新で再束縛——ミリ秒遅延・ゼロデータ複写・完全 prompt cache 保持。宛先鍵が他セッション占有中は自動解除して競合回避。

**セッションポリシー：** 転送後動作の三式——`persistent`（不 reset）、`daily`（設定時刻 reset）、`idle`（不活性 reset）。エージェント身元（`agent_id`）は転送をまたいで保持。同一Agent人格・ツール・メモリが新チャネルで継続。

**試験範囲：** unit 17＋API統合7＝24試験。全辺縁（競合解決・同チャネル拒否・非活性ペアリング・エージェント保持・ポリシー式）。

### 自動「ブラウザで続ける」ボタン

エージェントの全IM返答の底に**「ブラウザで続ける」**ボタン自動付き。タップでWeb UI会話頁を全開——ツール呼出手順・コード差分・ファイル履歴付きワンクリック。

- **精密振分** — ボタンはDB Chat UUIDで`/{chatUUID}`リンク（IM側peer IDでない）。常時正確会話を開く
- **バックグラウンドタスク通知** — `/btw`完了のIM通知にも同ボタン付き
- **優雅劣化** — 対話ボタン非対応チャネル（例WeChat）は自動で文面リンクにフォールバック。公開URLなし時は返答を block せず黙って省略
- **WebUI濾過** — Web UI内メッセージにボタンなし（冗長自己リンクなし）

**試験範囲：** 22試験（unit 11＋統合8＋回帰3）。URL構築・DB UUID解決・チャネル濾過・異常処理・優雅劣化。

## セッション継続と文脈保持

IM経由リモート操作は文脈を決して欠損しない——四層が継ぎ目なし継続を保証：

| 層 | 動作 |
|-------|-------------|
| **セッション方策** | Persistent（不 reset）・Daily（毎朝 fresh）・Idle（N分不活性で reset）から選択 |
| **自動 reset 通知** | セッション reset 時、エージェントに「新規会話」告知＋ユーザーに通知——以前文脈の幻覚参照なし |
| **履歴 backfill** | コールドスタート時、チャネル直近15通を自動 replay して即文脈 |
| **共有コンテキスト** | cross-agent・ cross-channel メモリ共有——デスクトップ開始作業はモバイルIM切替で継ぎ目なし継続 |

メッセ転送架构（例Coze → Claude Code）と違い、 transit で workspace 文脈を欠損しません。Myrmエージェントは workspace 直上で動作。完全ファイル系到達、linter実行、git status確認、 project tree 探索——IDE状態同期層不要。

## IMでUndo・Retry・ファイル復元

任意IMチャネルで`/undo` or `/retry`送信。エージェント前ターンを巻戻し——**自動ファイル復元付き**。

| コマンド | 動作 |
|---------|---------|
| `/undo` | 直近ユーザー＋アシスタント文 pair 削除**かつ**当ターン変更ファイルを復元 |
| `/retry` | 直近アシスタント返答を削除しファイル変更を戻し、**元質問を再送**して fresh 回答 |

**仕組み：** エージェントのメッセージ処理時、一貫`message_id`をAgent SnapshotStoreからDBまで追跡。`/undo`で削除文ID群を回収し、対応ファイルスナップショットを探索復元。ユーザーは地域化確定文を見る（例「↩ Undone: 2 message(s) removed. ↩ Reverted 3 file(s).」）。

**意義：** 競合（OpenClaw・Hermes・DeerFlow）のファイル revert はデスクトップGUIやCLIのみ。他製品にIMチャネル内undo/retry連動ファイル revert は存在しません。つまりスマホからエージェントにファイルを触らせて安全——失敗時は`/undo`一発で修復。

## チャネル自己回復と信頼性

全チャネルは**ChannelGateway**下で稼働。ヘルスを継続監視し自動回復——人手不要。

### ヘルスループ

gateway は定期ヘルス検査周期（60秒間隔）。2連続失敗で**DEGRADED**入り自己回復管発火：

1. **指数バックオフ** — 再起動遅延5秒→最大300秒。資源 thrash 防止
2. **ジッタ** — 25% random 変動。複数同時失敗の thundering herd 防止
3. **完全再起動** — `stop()`（全 handle 解放）→`start()`（ fresh 初期化）実行
4. **状態放送** — フロントエンド`ConnectionBadge`がEventEmitter経由リアルタイム更新

### メッセージ回復（InboundJournal）

クラッシュ window 受信メッセージは**決して欠損しない**。`InboundJournal`が処理前に inbound 永続。 再起動時、未処理エントリを自動 replay して振分管へ——ユーザーはクラッシュを知らない。

### Dead Letter Queue

複数再試行失敗メッセージは全メタ付きDLQへ。検査・再試行・アーカイブ可——黙って消えない。

### 汎用再接続ループ

WebSocket系チャネル（Discord・Slack・Feishu等）は共通`reconnect_loop`（指数バックオフ＋ジッタ）共有。長時間接続に一貫・実戦的再接続動作。

### プラットフォーム固有流量制限

チャネルごとに**TokenBucket**流量制限をプラットフォームAPI上限に調整。WeChat系は専用引数：

| チャネル | 流量 | 効果 |
|---------|------|--------|
| WeChat（iLink） | 2 msg/s | 個人垢 throttle 防止 |
| WeChat Official | 1 msg/s | Official Account API quota 尊重 |

プラットフォーム流量制限誤り時（WeChat errcode 45011/45015/45047 or iLink errcode -2）：

1. 誤りを`retry_after`付きプラットフォーム固有`RateLimitError`に対応付け
2. `retry_after`尊重の指数バックオフ再試行
3. 再試行尽きはDLQへフォールバック——文面メッセージは黙って落とさない

### サーキットブレーカーと優雅劣化

チャネル outbound API連続失敗時、二重保護層発火：

**チャネルレベルサーキットブレーカー** — 送信5連続失敗でサーキット発火。 outbound 配送を30秒休止。メッセージはPriorityQueue（最大256）に安全待機し、サーキット閉で配送。劣化プラットフォームAPI洪水を防止。

**streaming 優雅劣化** — ライブ streaming 更新中（リアルタイム文面編集等）の失敗は、即断でなく5段階漸進減速：

| 層 | 倍率 | 効果 |
|-------|-----------|--------|
| NORMAL | 1× | 標準更新頻度 |
| DEGRADED_1 | 2× | 微減速 |
| DEGRADED_2 | 4× | 体感遅延、応答は維持 |
| DEGRADED_3 | 8× | 顕著遅延 |
| DEGRADED_4 | 16× | 最大減速、更新は到達 |

核心原則：**ユーザーは常時更新受領**——劣化中は遅く到達するが、決して止まらない。30秒無音 blackout を作る伝統サーキットブレーカーより優越。

### ユーザー視点の意味

- **ゼロダウンタイム体験** — 一時網異常やプラットフォーム断は自己解決
- **メッセージ欠損なし** — サーバークラッシュでも namelijk メッセージは再起動回復
- **垢BANなし** — チャネルごと流量制限でプラットフォームAPI quota 超過防止
- **可視状態** — チャネルヘルスは設定＞チャネルで常時色バッジ可視
- **手動再起動なし** — チャネル自己回復。結果だけ見て回復過程は見ない
- **突発 blackout なし** — streaming 更新は abrupt 停止でなく優雅劣化

## リモート承認（HITL）

IMチャネル経由リモート操作時、高リスクツール呼び出し（ファイル編集・シェル命令）は**in-channel承認プロンプト**発火——業界唯一のIMネイティブHITL系。

### 仕組み

1. エージェントが危険ツール呼び出しに遭遇
2. 承認/拒否ボタン付きメッセージをIMチャネルへ送信
3. 承認・拒否・一括命令で応答
4. エージェントは判断で再開 or 停止

### 承認方法

| 方法 | 例 |
|--------|---------|
| スラッシュコマンド | `/approve`・`/deny`・`/approve-always` |
| 理由付き拒否 | `/deny <reason>` — エージェントが理由で手法調整 |
| 短縮 | `1`（承認）、`2`（拒否）、`y`、`n` |
| 絵文字リアクション | 👍（一度）、♾️（常時）、👎（拒否） |
| 一括 | `/batch a,d,a`（承認・拒否・承認） |
| 中国語 | `同意`、`拒绝`、`是`、`不` |

### 対話ボタン（ActionButton）

対話要素対応チャネル（Telegram InlineKeyboard・Slack Block Kit・Discordボタン・Feishuカード・MS Teams Adaptive Card）では承認プロンプトにネイティブ**承認 / 拒否ボタン**付き。ボタンクリックで：

1. DBで承認を解決（PENDINGのみ——重複クリック安全無視）
2. 元メッセージを結果表示に編集（例「Approved by alice」）
3. 中断エージェントを自動再開

WebUI承認と併用可——両経路とも同一永続記録へ。

### セキュリティ

- **グループ chat 保護**：元要求者 or 設定共同承認者のみ承認可
- **冪等ガード**：解決済み承認の再解決・状態反転不可（DB層PENDING検査）
- ** timeout ガード**：未回答承認は自動拒否（設定可）
- **永続許可リスト**：「常時許可」判断は再起動をまたいで保持
- **再試行防止**：3拒否でエージェント再試行停止

## Outbound HITL（下書き査読）

企業営業・顧客対応シナリオでは、AI生成返答の送信前に人間査読が必要な場合あり。Myrmの**Outbound HITL**はエージェント返答を下書きとして差し止め、明示承認を要求。

### 設定

トピックごとに**設定 → チャネル振分**で独立設定：

| 設定 | 選択肢 | 説明 |
|---------|---------|-------------|
| 返答式 | 自動 / 下書き査読 | 自動は即送信。下書き査読は承認待ち保持 |
| Timeout | 1分 – 1時間 | 自動動作までの待機 |
| 期限時 | 自動拒否 / 自動送信 | 誰も査読しない時の動作 |

### 仕組み

1. IMチャネルにメッセージ到達→エージェントが返答生成
2. 返答を差し止めて`ApprovalRecord`に保管（未送信）
3. 査読者はWebUI承認ドロワー or IM ActionButtonで下書き確認
4. **承認** → チャネルへ送信
5. **拒否** → 文面破棄
6. **Timeout** → 設定可の自動送信 or 自動拒否

### 査読チャネル

- **WebUI承認ドロワー**：元顧客文・AI生成下書き・チャネル/トピック情報を表示
- **IM ActionButton**：チャネル内承認通知の承認/拒否ボタン

### 用途

| シナリオ | 下書き査読の理由 |
|----------|-----------------|
| 顧客見積/価格 | 誤価格は法責任を生む |
| 契約条項 | AIが非標準条項を幻覚する恐れ |
| コンプラ規制業種 | 金融/医療通信は査読必須 |
| ブランド敏感通信 | トーンと正確性が重要 |

## 賢い静粛濾過

エージェントの系プロンプトに「注目不要時は`[SILENT]`で返答せよ」等の指示がある場合、Myrmは配達前に静粛返答を自動検知濾過：

- **グループ chat**：エージェントがメンションされ確認、注目なし→無送信（ゼロ騒音）
- **予約タスク**：定期検査が正常→自動静粛。 issue 時のみpush
- **プレースホルダ清掃**：「処理中…」プレースホルダ文は黙って除去

### 検知則

| 書式 | 静粛？ |
|--------|:-------:|
| `[SILENT]` | ✅ |
| 空白付き `  [SILENT]  ` | ✅ |
| Markdown fence 包み | ✅ |
| `[SILENT] nothing to report` | ❌ 通常配送 |
| 他文あり | ❌ 通常配送 |

「要時のみ通知」体験を保証——エージェントは意味ある用件があるときだけIMチャネルへ送信。

3. **冪等 Patch 再演 Depot**：成功デプロイレシピを冪等`deploy.sh`に `[0/N]`段階標記付きパッケージ。 downloadable artifact でソフトウェア更新後の継ぎ目なし再演

2. **証拠錨付きワンクリック週報（`WeeklyReportSOPService`）**：複鎖テレメトリを構造化Markdown報告とFeishu・WeCom・DingTalk・Telegram向けネイティブリッチ対話カードに幻覚なし変換
3. **Chat-to-Knowledge自動アーカイブ**：協働 chat 流から設計判断・技術合意・会議結論を自動抽出してローカル/クラウドWiki知識ベースへ原子書込

### マルチチャネルDMセッション Enclave と毒化防止ゲート

複数ユーザー・同僚・顧客が同一エージェント instance に送信チャネル経由対話時（Feishu・WeChat・Telegram・Slack等）：

1. **4-Tuple物理セッション Enclave（`routing_enclave_key`）**：`(tenant_id, channel, peer_id, agent_profile_id)`で厳格隔離。テナント・チャネル・送信者・複数エージェント人格をまたぐ会話混線とデータ漏洩を物理防止。後方互換2-tuple `parse_enclave_key`解決を継ぎ目なく維持
2. **見知らぬ者権限昇格防御ゲート（Anti-Privilege Escalation Gate）**：OPEN策で未ペア送信者が`default_user_id`（sandbox superuser権限）継承に自動 fallback する重大脆弱性を閉鎖。未ペア送信者は厳格に隔離 guest 身元（`guest_{channel}_{sender_id}`）を割当て、特権実行ツール到達ゼロ
3. **長期記憶毒化防止 Fence（Anti-Poisoning Fence）**： inbound 永続管`record_inbound`で認証状態を直接検証。 visitor と未ペア文は厳格に`learning_eligible=False`刻印。 prompt injection による長期記憶・ベクトル索引汚染を物理 block

## 統一 cross-channel ネイティブ承認

モバイルIMチャネルからAI相棒をリモート操作時、高権限操作（cron予定変更や機密ツール呼出等）はMyrm統一ネイティブ承認管（`ApprovalRegistry`）で警護：

- **非 block 非同期並行**：CLI系競合 daemon に多い単一ファイル`fcntl.flock` deadlock に完全免疫
- **適応複合カード界面**：
  - **Feishu / DingTalk / Telegram / Slack / Discord**： chat 流にネイティブ`ActionButton`要素付き対話カードを直接配送（`✅ 承認` / `❌ 拒否`）
  - **WeChat / iMessage / SMS**：文面命令解析（`/approve`）とApple Watch Tapback 👍絵文字身振りに継ぎ目なく劣化
- **複数クライアントリアルタイム同期**：スマホ解決の承認はWebUI（`CronJobCard`）とデスクトップへSSE/WebSocket即push。手動頁更新なし

## チーム身元：全グループ chat の名付き仲間

グループ chat に名付き共有身元を与え、全員が同一Arielと会話：

1. **設定 → 統合 → チャネル振分**を開き、チャネルとトピックを選び、名を打つ（例`Helper`）。範囲選択：**継承**（チャネル基準）・**共有**・**私有**（独立、基準継承なし）
2. グループで言及（`@Helper, research this and file it to our topic library`）——スレッド内応答し、議論を自己記憶区画に記憶。あなたのDMは決して見ない
3. グループターンはあなた個人トークンに触れない共有認証情報で動作。DMは常時 personal
4. 身元はいつでも凍結可（振分は既定エージェントへ fallback、記憶保持）or `/topic`状態確認。 chat 内では：`/bind agent=my-agent identity=Helper identity_scope=shared`

## 能動追跡：受領と停滞 nudge

長時間 job と静寂スレッドは見守りなしで閉じる：

1. 同一チャネル振分行で**完了受領**を有効化（長時間作業完了時に元スレッドへ配送カード投稿）＋任意で**停滞 nudge**（未完項目ありスレッド静寂時に@言及一発）
2. 全能動文はAIバッジ付き＋承認ゲート先行——査読保留下書きは決して自動投稿しない
3. 任意スレッドを`/mute`で黙らせる。凍結身元は決して能動送信しない
