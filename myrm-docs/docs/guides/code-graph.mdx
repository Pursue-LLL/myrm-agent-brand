# Code Graph Queries

Before you change a function's signature you need its call sites. A text search for a common name returns every unrelated match, and a long result is cut off without telling you what was lost. The **`repo-call-graph`** skill adds one tool, `code_graph_tool`, that answers structural questions about your code and labels how far each answer can be trusted.

## What you can ask

Ask in plain words, such as "who calls `select`?". The agent picks the action.

| You ask | Action | What comes back |
|---|---|---|
| Where is it defined? | `resolve`, `definition` | Qualified name, kind, file and line span; `definition` adds the doc comment |
| Who calls it? | `callers` | Each call site, with the function that contains it |
| What does it call? | `callees` | The calls made inside the function |
| Which classes extend it? | `implementors` | Subclasses and where they are declared |
| Who imports this module? | `importers` | Importing files (Python only) |
| Which tests call it? | `tests_calling` | The tests that call it directly |

Python and TypeScript/JavaScript are covered.

## Turn it on

1. Open **Settings → Skills** and switch on **`repo-call-graph`**.
2. The **Skill Permission Approval** dialog asks for **Read File**. Choose **Approve**, pick a permission template that includes it (for example **Data Analysis**), or **Deny**.
3. Open a chat whose agent has a workspace folder, such as a project folder you linked, and ask your question.

The skill is off by default. **Deny** leaves it off and stores nothing, so switching it on again asks again; so does revoking the permission later. After you approve, calls run without further prompts because the tool only reads files.

## Read the answer

An answer to "who calls `select`?", abridged:

```json
{"action":"callers","query":"select","total":2,"rows":[
  {"at":"app.py:5","caller":"app","callee":"select","match":"exact","args":1},
  {"at":"app.py:6","caller":"app","callee":"db.select","match":"name","args":1}],"definitions":1}
```

- **`match`** (call-site answers: `callers`, `tests_calling`): `exact` means the call text is the name you asked for. `name` means only its last part matches, so `db.select(...)` could be a different function that shares the name.
- **`definitions`** (same two actions): how many definitions share the name. Above 1, read each `name` row before you rely on it.
- **`total`** (every action): the full count. At most 50 rows are shown, with the call sites most likely to reach the definition listed first; past 50 the answer adds a per-file count and a hint for narrowing it.
- **Letter case matters**: `select` does not match `db.Select(...)`.

## What it does not do

- It matches names. It does not infer types or follow imports, so a language server is more precise for semantic questions. Dynamic calls (`getattr`, strings, decorators, dependency injection) are invisible, so an empty result is not proof that nothing calls the function.
- Imports are indexed for Python only. Git-ignored files, dependency and build folders, files over 1 MB, symbolic links and Python files with syntax errors are not indexed, and an oversized workspace is indexed in part; the answer's `notes` say when that applies.
- There is no graph picture. Answers are text rows in the chat.
- The first call on a large repository builds the index, which takes seconds to tens of seconds; later calls re-read only the files that changed. The index sits outside your workspace in the app's data folder and takes roughly four times the size of the source.
