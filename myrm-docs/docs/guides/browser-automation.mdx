## Page Understanding — Dual-Path ARIA Snapshot

Myrm uses a **semantic accessibility tree** instead of raw DOM for page understanding. This means your agent sees the page the way a screen reader does — structured, noise-free, and focused on interactive elements.

### How It Works

| Path | When Used | Speed | Method |
|------|-----------|-------|--------|
| **Fast Path** | 90% of pages | 5-10ms | Playwright native `ariaSnapshot()` — zero JS injection |
| **Custom Path** | Complex edge cases | 20-50ms | JavaScript traversal with depth control |

### What the Agent Sees

Instead of thousands of DOM nodes, the agent gets a clean semantic tree:

```yaml
- heading "Sign In" [level=1]
- textbox "Email" [ref=1]
- textbox "Password" [ref=2]
- button "Log In" [ref=3]
- link "Forgot password?" [ref=4]
```

Every interactive element gets a stable **ref ID** that the agent uses for precise targeting — no fragile CSS selectors.

### Built-in Resilience

- **Shadow DOM traversal** — Sees through Web Components automatically
- **iframe extraction** — Cross-origin iframes included in the tree
- **Scope filtering** — `full`, `interactive`, or `focused` views for token efficiency
- **Incremental diff** — Only shows what changed between snapshots

### Why Not Occlusion Detection?

Some tools (like OpenCLI) scan every element with `elementFromPoint` to prune occluded elements. We deliberately don't do this because:

1. It adds 100-500ms per snapshot (reflow for every element)
2. It can accidentally prune valid elements (dropdown menus, tooltips)
3. Playwright's `click()` already refuses to click covered elements
4. If a click fails, our **Self-Healing Locator** fixes it in O(1) time

Net result: 5-10ms snapshots that are 60-80% smaller than DOM-based approaches, with zero accuracy trade-offs.

## Smart Infinite Scroll

Pages with lazy-loading content (social feeds, e-commerce catalogs, news sites) normally require 10-20+ scroll-and-check loops. Each loop costs one LLM call.

Myrm's `scroll_to_bottom` action handles this in **one call**:

1. Agent calls `browser_interact(action="scroll_to_bottom")`
2. The engine automatically scrolls one viewport at a time, waiting for new content to load
3. When the page height stops growing for 3 consecutive checks, it stops
4. Returns a summary: steps taken, time elapsed, height change, and completion status

**Result**: One tool call replaces 10-20 LLM roundtrips — saving ~90% token cost per infinite scroll page.

Configurable via parameters: `max_steps` (how far to scroll), `delay_ms` (wait time between scrolls), `stable_count` (how many stable checks before stopping).

## Dialog Policy (Handling Popups Automatically)

JavaScript dialogs (`alert`, `confirm`, `prompt`, `beforeunload`) can block all page interaction if not handled. Myrm provides **four configurable policies** per agent:

| Policy | Behavior | Best for |
|--------|----------|----------|
| **Smart** (default) | Accept alerts/confirms, dismiss prompts | General browsing |
| **Auto Accept** | Accept all dialogs | Bulk automation, scraping |
| **Auto Dismiss** | Dismiss all dialogs | Data extraction, read-only |
| **Wait for Agent** | Pause and let AI decide (with timeout fallback) | Critical confirmations |

### Configuration

Set the dialog policy per agent in **Settings → Agents → Capability Config → Dialog Handling**.

The agent can also switch policy at runtime using the `dialog_policy` action in `browser_manage`.

### How It Works

- In **Smart** mode (default), your agent never gets stuck on cookie banners or info alerts.
- In **Wait for Agent** mode, the dialog content appears in the next browser snapshot, giving the AI full context to decide. If the agent doesn't respond within the timeout, a safe fallback fires automatically.
- Dialog history is always visible to the agent — it knows what popups were handled and how.

## Schema-Driven Structured Extraction

Instead of dumping raw page text into the conversation (which wastes context tokens), you can pass a **JSON Schema** to the extraction tool and get back validated, structured JSON.

### How it works

1. Agent calls `browser_extract` with an `extraction_schema` parameter (a JSON Schema string).
2. The tool extracts the page text, then uses an LLM to produce structured output matching your schema.
3. You receive clean, validated JSON — not thousands of tokens of raw HTML.

### Example

Ask the agent: *"Extract all product names and prices from this page"*

The agent uses a schema like:

```json
{
  "type": "array",
  "items": {
    "type": "object",
    "properties": {
      "name": { "type": "string" },
      "price": { "type": "string" }
    },
    "required": ["name", "price"]
  }
}
```

Result: a clean JSON array with just the data you need.

### Key Features

- **Object and Array schemas** — Extract a single object or a list of items.
- **Pagination deduplication** — Pass `already_collected` to avoid duplicates across pages.
- **Dual-strategy reliability** — Preferred `structured_output` with raw JSON fallback for model compatibility.
- **Token savings** — 70–97% reduction compared to raw text extraction.
- **Schema complexity protection** — Limits on property count and nesting depth prevent misuse.

### From Extracted Data to Interactive Spreadsheet

Once you have structured JSON from extraction, the agent can write it to a CSV or Excel file — which automatically becomes a rich, interactive artifact in the chat.

**The pipeline** (fully automatic, no extra tools needed):

1. Agent extracts structured data via `extraction_schema`
2. Agent writes a `.csv` file using the built-in file tool → artifact auto-registered
3. Frontend receives the artifact via real-time SSE push

**What users see in the DataGrid:**

For Excel (`.xlsx`) files with multiple sheets, the agent can use the code execution tool with Python's `openpyxl` — the frontend automatically shows sheet tabs for switching between sheets.

**vs competitors:** Most browser automation tools (e.g., BrowserAct) only produce a downloadable file. Myrm delivers data as a **live, interactive table** inside the conversation — users can explore, sort, and search before downloading.

## Vision Auto-Fallback (DOM → LLM)

When a page renders content via Canvas (charts, graphs) or complex SVG (infographics, diagrams), traditional DOM text extraction returns empty or meaningless data. Myrm automatically detects this situation and falls back to Vision LLM-based extraction — transparently, without any agent intervention.

### How it works

1. Agent requests page text extraction (same `browser_extract` tool as always).
2. If DOM text is insufficient (<50 chars) AND the page contains significant visual elements (large Canvas/SVG), the tool automatically takes a screenshot.
3. A Vision LLM analyzes the screenshot and extracts all visible text, data, labels, and values.
4. The result is returned to the agent — identical interface, richer data.

### When it triggers

- **Charts/dashboards** (rendered via Chart.js, D3, ECharts in Canvas)
- **Infographics** (complex SVG with embedded text/data)
- **Canvas-rendered applications** (Google Maps data, game UIs)
- **Image-heavy content pages** (where meaningful text exists only in visuals)

### Key features

- **Fully transparent** — The agent doesn't need to know about the fallback; same tool, same schema.
- **Smart detection** — Only activates when Canvas/SVG elements exceed 200×100 pixels (avoids false triggers on small icons).
- **SVG text extraction** — Even without Vision LLM, SVG `<text>` and `<tspan>` elements are now extracted directly from DOM.
- **Structured output** — Works with schema-driven extraction too — Vision LLM produces JSON conforming to your schema.
- **Zero extra cost when not needed** — If DOM text is sufficient, no screenshot or LLM call is made.

### Competitor comparison

## On-Demand Media Extraction

Extract all images, videos, and audio URLs from any page with a single tool call — no JavaScript writing required.

### How it works

1. Agent calls `browser_extract(mode='media')` — one tool call.
2. The tool traverses all frames and collects:
   - **Images**: `<img>` tags with lazy-load resolution (`data-src`, `data-lazy-src`, `data-original`, `srcset`, `data-srcset`, plus wildcard `data-*src*` fallback for any lazy-loading library)
   - **Videos**: `<video>/<source>` elements + iframe embeds (YouTube, Vimeo, Dailymotion, Wistia)
   - **Audio**: `<audio>/<source>` elements
   - **Meta images**: OpenGraph and Twitter Card image tags
3. Decorative elements (icons, logos, favicons, tiny images <50px) are automatically filtered out.
4. Cross-frame URL deduplication ensures clean, duplicate-free output.
5. Results include dimensions, alt text, and poster URLs where available.

### Key advantages

- **On-demand** — Only extracted when needed, unlike competitors that dump media in every response.
- **Selector scoping** — Use the `selector` parameter to extract media from a specific page region.
- **Lazy-load aware** — Resolves all common lazy-loading patterns including `data-srcset` and wildcard `data-*src*` attributes.
- **Cross-frame dedup** — Extracts from all iframes with automatic URL deduplication across frames.
- **Structured output** — Grouped by type (Images/Videos/Audio/Meta) with counts and metadata.

### Example

Ask the agent: *"Extract all product images from this e-commerce page"*

The agent uses `browser_extract(mode='media', selector='.product-gallery')` and gets a clean list of image URLs with dimensions — no JavaScript needed.

## Ephemeral Session Isolation

Every browser context is **ephemeral by default** — created via `browser.new_context()` with no persistent profile. Cookies, localStorage, and cache are automatically destroyed when the session ends. The agent never has access to your real browser profile, eliminating session leakage risk entirely.

## Persistent Session Vault (Cross-Session Login)

While sessions are ephemeral by default, you can configure **auto-restore domains** for each agent to preserve login state across conversations.

### How It Works

1. **Configure domains** — In the agent settings WebUI, add domains like `twitter.com`, `github.com` to the agent's `auto_restore_domains` list.
2. **Sessions are encrypted** — Cookie and storage data saved via AES-256-GCM encryption in the Session Vault.
3. **Auto-restore on startup** — Every time the agent launches a new browser session, configured domains have their login state automatically restored.
4. **Agent can manage explicitly** — The agent can also call `browser_manage(action="save_session")` / `restore_session` / `list_sessions` / `delete_session` for fine-grained control.

### Architecture

- **AES-256-GCM encryption** — Session data is encrypted at rest, never stored in plaintext.
- **O(1) LRU memory cache** — Hot sessions served from memory; no disk I/O on repeated access.
- **Singleflight dedup** — Concurrent requests for the same domain are coalesced into one decrypt operation.
- **TTL auto-expiry** — Stale sessions are garbage-collected automatically.
- **Full execution coverage** — Works across Web, Channel, Cron, and Eval execution contexts.

### When to Use

| Scenario | Recommendation |
|----------|----------------|
| One-off browsing | Default (ephemeral) — no config needed |
| Repeated access to authenticated sites | Add to `auto_restore_domains` |
| Agent workflow needs login mid-task | Agent calls `save_session` / `restore_session` |
| Shared credentials across agents | Each agent configures its own domain list independently |

### Session–Memory Bridge (Zero-Cost Awareness)

When the memory system is enabled, saved browser sessions are **automatically visible** in the agent's context — no extra tool call needed.

- **How it works:** Every time a session is saved or deleted, a `SessionMemoryBridge` updates the agent's `active_browser_sessions` profile attribute. This attribute is injected into every LLM turn via the memory context middleware.
- **Result:** When a user says "post a tweet", the agent already knows `twitter.com` is available — it calls `restore_session("twitter.com")` directly, **skipping the `list_sessions` step** and saving one LLM inference round.
- **Prompt cache safe:** The profile attribute only changes on save/delete (very infrequent), so prompt prefix caching is unaffected.

| Without Bridge | With Bridge |
|---------------|-------------|
| User: "Post a tweet" → Agent calls `list_sessions` → sees twitter.com → calls `restore_session` | User: "Post a tweet" → Agent sees twitter.com in context → calls `restore_session` directly |

3. **Agent connects** — When a task requires browser access to an authorized domain, the agent connects to your real browser through the extension's WebSocket channel and `chrome.debugger` API.

### Background Window Isolation (Non-Perceptive Execution)

When the agent operates via Extension Bridge, all automation runs in a **dedicated background window** — your active tabs are never touched:

- The extension creates an invisible non-focused window (`focused: false`) for agent tasks
- All tab operations happen in this isolated window — no focus stealing, no tab switching
- The background window ID persists across Service Worker restarts via `chrome.storage.local`
- If you manually close the background window, it's automatically recreated on next task
- On disconnect, all background tabs are cleaned up to prevent resource accumulation

**Result**: You continue browsing normally while the agent works in the background at full speed. No window flashing, no focus stealing, no disruption.

### Security Model

- **Domain-level authorization** — Only explicitly authorized domains can be controlled. The agent cannot access any tab outside your allow-list.
- **Token authentication** — The extension authenticates to the server with a secret token, preventing unauthorized connections.
- **Service Worker keepalive** — The MV3 extension uses `chrome.alarms` for persistent connection with exponential backoff reconnection.
- **Domain sync on reconnect** — When the extension reconnects, it immediately synchronizes authorized domains with the server.

### Frontend Management

The Extension Bridge settings panel (Settings → Integration) provides:

- **One-click copyable WebSocket URL** — The correct connection URL for your deployment mode, with a Copy button and toast confirmation
- **Auth token status** — Shows whether `EXTENSION_AUTH_TOKEN` is configured on the server (without exposing the token itself)
- **Copyable extension path** — Shows `~/.myrm/myrm-agent/myrm-agent-extension` with one-click copy for Chrome's "Load unpacked" dialog
- **Step-by-step setup guide** — Appears when extension is not connected: Load unpacked extension → Copy URL → Connect
- **Real-time connection status** — Connected/disconnected indicator with extension version and browser name
- **Domain authorization management** — Add, remove, and wildcard pattern support
- **Available tabs list** — Filtered by authorized domains, shows active tab indicator

### Architecture

The Extension Bridge spans 5 layers:

1. **Harness Protocol** (`ExtensionBridge`) — Defines the contract at the framework level
2. **Server Service** (`ExtensionBridgeService`) — Manages WebSocket lifecycle, heartbeat, and tab control
3. **API Router** — WebSocket + REST endpoints for extension and frontend
4. **Chrome Extension** — MV3 Service Worker with chrome.debugger attachment capability
5. **Frontend Panel** — React settings component for status and domain management

### Side Panel Chat — AI Assistant Alongside Every Webpage

The Chrome Extension includes a **Side Panel** that opens alongside any webpage, providing an immersive chat experience without leaving the current page.

**Key capabilities**:

- **Context-aware conversations** — Every message automatically includes the current page title and URL, so the agent understands what you're looking at
- **Text selection forwarding** — Select text on any page, and it appears as a quoted reference in the chat input. Right-click → "Ask Myrm about this" sends it directly

## Per-Agent Browser Configuration (4-Axis Control)

Each agent has four independent browser configuration axes, all configurable in the WebUI Settings → Agents → Capability Config:

| Axis | Options | Default | What It Controls |
|------|---------|---------|------------------|
| **Browser Engine** | Chromium (Patchright) / Firefox (Camoufox) | Chromium | Which stealth engine is used for launched browsers |
| **Browser Source** | Auto / Extension / Launch | Auto | How the agent accesses a browser instance |
| **Dialog Policy** | Smart / Auto Accept / Auto Dismiss / Wait for Agent | Smart | How JavaScript dialogs are handled |
| **Session Recording** | Off / On Failure / Always | Off | Whether browser sessions are recorded for debugging |

### Browser Source Modes

| Mode | Behavior | Best For |
|------|----------|----------|
| **Auto** (default) | System decides based on availability | General use — no manual setup needed |
| **Extension** | Uses your real browser via the Extension Bridge | Shopping, social media, any task needing login state |
| **Launch** | Spins up a fresh managed browser instance | Research, data extraction, testing |

### Hybrid URL Routing (Cloud/SaaS)

When running in cloud mode, agents cannot directly access your private network (localhost, 192.168.x.x, internal services). Myrm automatically detects private URLs and routes them through the Extension Bridge:

- **Public URLs** (google.com, github.com) → handled by the cloud sandbox browser (normal, fast)
- **Private URLs** (localhost:3000, jira.internal, 192.168.1.1) → transparently routed through your Extension Bridge

This means your cloud-hosted agent can interact with local development servers, internal dashboards, and corporate tools — all through your already-logged-in browser. No VPN tunnels, no ngrok, no public exposure of internal services.

If the Extension Bridge is not connected when a private URL is encountered, the agent will inform you and suggest installing the extension.

### How to Configure

1. **Agent Creation**: Settings → Agents → Create/Edit → Capability Config
2. **Per-Chat Override**: Click the agent config icon in the chat window → Browser settings

All four settings persist across agent clone, export/import, and API operations. Invalid values are rejected at the API layer before reaching the database.

### Pool Isolation

Every agent session operates in its own **Chromium BrowserContext** — a browser-level security boundary equivalent to running separate browser profiles. This means:

- **Cookie/Storage hard isolation** — Agent A's login sessions, cookies, and localStorage are physically invisible to Agent B. No software check needed; the browser itself enforces the boundary.
- **Tab isolation** — Each agent's TabController manages only its own tabs. Agents cannot switch to, close, or even enumerate tabs belonging to other sessions.
- **Extension-source separation** — Extension-sourced browsers (unmanaged, your real sessions) are never shared with launch-mode agents (managed headless instances).
- **Automatic scaling** — New agents get new contexts without any registration or coordination. Tab limits are enforced per-context with LRU eviction.

This architecture is fundamentally stronger than software-based "tab ownership contracts" used by browser extension agents — those can be bypassed by bugs, while BrowserContext isolation is enforced by Chromium itself.

## Zero-Config Local Browser Discovery

When your agent is configured in **Auto** browser source mode (the default), Myrm automatically detects and connects to your already-running Chrome — **no configuration, no CLI flags, no environment variables**.

### How It Works

1. **DevToolsActivePort scan** — Myrm scans known browser data directories for the `DevToolsActivePort` file that Chrome writes when remote debugging is enabled.
2. **Multi-browser coverage** — Chrome, Edge, Chromium, Brave, and Chrome Canary are checked across macOS, Linux, and Windows.
3. **4-phase validation** — File scan → HTTP probe (`/json/version`) → TCP fallback (Chrome M144+ compatibility) → fixed port 9222 fallback.
4. **Graceful fallback** — If no running browser is found, Myrm launches a fresh managed instance instead.

### What You Need to Do

Just enable remote debugging in your browser once:

1. Open Chrome and navigate to `chrome://inspect`
2. Toggle **"Open dedicated DevTools for Node"** (this enables the debugging port)
3. That's it — Myrm will auto-discover Chrome from now on

### Why This Matters

| Without auto-discovery | With Myrm |
|----------------------|-----------|
| Must set `CDP_PORT=9222` env var | Automatic — just use the app |
| Must launch Chrome with `--remote-debugging-port` flag | Standard Chrome with inspect toggle |
| Only connects to one browser | Scans 5 browsers in priority order |
| No validation of stale ports | HTTP + TCP probes filter dead connections |

All discovery runs in a background thread so it never slows down the agent's event loop.

### IDE developer E2E (Cursor MCP) — use your real Chrome

When using MCP browser tools in Cursor (e.g. `ultimate-playwright-mcp`) for **logged-in frontend integration tests**, attach to **your Google Chrome** — not the default **Chrome for Testing** daemon some servers spawn on port 9223 (Cmd+Q won't stick; the daemon respawns it every 5s).

**Recommended MCP args**: `--cdp-endpoint http://127.0.0.1:9222`

**macOS one-liner** (dedicated debug profile, separate from daily browsing):

```bash
open -na "Google Chrome" --args \
  --remote-debugging-port=9222 \
  --remote-debugging-address=127.0.0.1 \
  --user-data-dir="$HOME/Library/Application Support/Google/Chrome-Remote-Debug" \
  --no-first-run --no-default-browser-check \
  "http://localhost:3000"
```

Use `open -na` for a fresh instance and `--remote-debugging-address=127.0.0.1` so MCP clients on `127.0.0.1` connect reliably. **Myrm product Auto mode** skips this — `chrome_discovery` finds your browser automatically.

If Chrome for Testing zombies appear: `pkill -f chrome-daemon; pkill -f "Chrome for Testing.*9223"`.

## Zero-Config Browser Setup

When you first use browser tools on a fresh Myrm desktop install, the browser engine (Chromium) is automatically downloaded and installed — **no terminal commands required**.

### How It Works

1. Agent requests a browser page for a task
2. If Chromium is not installed, Myrm detects the missing executable
3. Automatic download and installation runs in the background
4. The browser task continues seamlessly after installation

If automatic installation fails (no network, insufficient disk space, etc.), Myrm provides clear diagnostic messages with specific fix instructions.

### Smart Failure Handling

- **Cooldown protection** — After a failed install, Myrm waits 30 minutes before retrying to avoid blocking your workflow
- **Concurrency safe** — Multiple tasks requesting browsers simultaneously are serialized to prevent conflicts
- **Diagnostic messages** — Shows exactly what went wrong (disk space, network, permissions) and how to fix it
- **Doctor auto-fix** — Run `myrm doctor` with auto-fix to diagnose and repair browser issues

### Why This Matters

| Other Agent tools | Myrm |
|-------------------|------|
| Must run `playwright install chromium` in terminal | Automatic — just use the app |
| Windows dependency errors confuse non-dev users | Clear diagnostics with fix instructions |
| Browser features broken until manual setup | Works on first use |

## For contributors: pytest vs runtime browser cleanup

When browser integration tests time out or crash, orphaned Chrome/Patchright child processes can linger on the developer machine. Myrm separates concerns:

| Layer | Location | Purpose |
|-------|----------|---------|
| **Dev/CI only** | `tests/support/browser_process_cleanup.py` (Harness + Server copies) | `atexit` / pytest `sessionfinish` process-tree kill — **not shipped in the wheel** |
| **Runtime** | `GlobalBrowserPool` health checks, `doctor.py`, pool/singleton orphan sweep | Production browser hygiene for agents |

Hermes-agent mixes similar kill logic into production `browser_tool.py`; Myrm keeps pytest-only cleanup out of the agent runtime. Verified **2026-07-01**: 14 pytest items per repo (12 unit + 2 conftest wiring), 100% line coverage on the cleanup module.
