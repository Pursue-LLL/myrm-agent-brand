# Kanban & Sub-Agent Orchestration

Myrm provides a visual Kanban board for tracking complex, multi-step tasks and a powerful sub-agent system with 7 orchestration patterns.

## Kanban Task Board

The Kanban board gives you a drag-and-drop interface to manage agent tasks across 7 columns.

### Task States

| State | Description |
|-------|-------------|
| **Triage** | Rough idea just added — use AI Specify to refine into actionable description |
| **Backlog** | Tasks waiting to be scheduled |
| **Ready** | Dependencies met, available for pickup |
| **Running** | Currently being executed by an agent |
| **In Review** | Verified task awaiting human approval (`require_approval=true`) — approve → Completed, reject → Ready for rework |
| **Completed** | Successfully finished and verified |
| **Failed** | Execution failed (auto-retry or manual review) |
| **Blocked** | Waiting on external input or a dependency |
| **Archived** | Completed tasks moved out of the active board |

### Human Approval Gate (IN_REVIEW)

For tasks created with `require_approval=true`, the dispatcher parks a successfully verified task in **In Review** instead of completing it directly. An operator then approves it (→ Completed, releasing dependent tasks) or rejects it with a reason (→ Ready for rework, with the reason written back to the task's `error`). Manual status moves out of In Review are rejected with **409** — the gate cannot be bypassed by an LLM tool.

- **Idempotent**: approve/reject outside In Review are no-ops (double-submit safe)
- **Race-safe**: concurrent approvals succeed exactly once
- **Notified**: `REVIEW_REQUESTED` routes to the source chat via `BACKGROUND_TASK_DONE`
- **Traceable**: rejected reason + review history appear in the worker's context

No competitor (Hermes, OpenClaw, deer-flow, LobsterAI, CoPaw, jiuwenclaw) offers a task-level human approval gate. Kanban lifecycle is now **9 states + 23 events**.

**Verified (2026-08-09)**: harness `test_in_review.py` 11/11 + server `test_in_review_api.py` 14/14 = 25 tests, 0 failures.

### Pending-Review Visibility & Direct Access

Once a task enters **In Review**, you never have to hunt for it:

- **Global pending count** — every task awaiting your approval (across all projects) aggregates into a global counter in the navigation badge and the Fleet overview's **Pending** card, so nothing gets missed.
- **One-tap deep links** — clicking a web-push / IM review notification jumps straight to the board's **In Review** column; the global Pending card deep-links the same way. Deep links auto-locate the target board even when the task lives in a different project than your current filter.
- **Status filter** — filter any board to show only in-review tasks.
- **Approve / reject from the drawer** — approve completes the task and auto-advances dependents; reject writes the reason back and returns it to Ready. Counts update in real time.

**Verified (2026-08-11)**: Chrome E2E drives the full real flow (seed → drawer approve/reject → global KPI +1/-1 → KPI click-through to the in-review column → status filter) — 1 passed in 153s.

### Task-Level Skill Configuration

Each task carries its own `extra_skill_ids` — a per-task skill overlay merged into the worker's tool set at startup (`agent_skill_ids = profile.skill_ids + task.extra_skill_ids`). Three safeguards make this configurable, validated, and honest:

| Safeguard | Behavior |
|-----------|----------|
| **GUI skill picker** | The create form and task drawer use a searchable multi-select backed by the same skill library as the agent panel — no more typing skill ids from memory. Removed ids stay visible labeled "unknown" instead of being silently dropped |
| **API existence validation** | `extra_skill_ids` are validated against the full discoverable set (PREBUILT + LOCAL + WORKSPACE). Unknown ids are rejected with `400` plus a hint listing available skills — a task can never be silently "configured but not applied" |
| **Running-task semantics** | Editing skills on a `running` task shows "takes effect on next run". Skills are bound when the worker starts (keeping the prompt cache maximized), so mid-run edits never silently no-op |

Internal task-creation paths (decompose/specify, pipeline instantiation) bypass the user-facing validation by construction — decompose does not emit skill ids and pipelines only inject template-defined skills.

### Role-Based Kanban LLM Tools

Kanban tools are **opt-in** and **role-gated** to save tokens and reduce misuse:

| Context | Tools bound | Count |
|---------|-------------|------:|
| Default chat (Kanban off) | None | 0 |
| Chat with Kanban enabled | Orchestrator set (add, list with optional stats, unblock) | 3 |
| Kanban task worker | Worker set (show, complete, block, heartbeat, comment, attach) | 6 |

Board create/list CRUD stays **REST/GUI only** — no LLM tool slots wasted. Use `kanban_add_task.depends_on` for DAG edges; `kanban_list_tasks` accepts optional `task_id` for single-task lookup and `include_stats=true` for board counts. Board listings default to **50 tasks** (max 200) with `truncated` metadata when more rows exist — aligned with the REST API and Hermes.

Hermes users migrating to Myrm get the same **worker vs orchestrator** split, plus a visual Kanban GUI, DAG scheduling, and CompletionVerifier. OpenClaw has a display-only Workboard with **zero** LLM tools; deer-flow / LobsterAI / CoPaw / jiuwenclaw expose **zero** native Kanban LLM tools.

### Architecture-Level Anti-Lie

Hermes implements runtime `_verify_created_cards` + `_scan_prose_for_phantom_ids` to detect when an agent falsely claims it created sub-tasks. This is necessary because Hermes gives **every** agent both `kanban_create` and `kanban_complete` tools.

Myrm solves this structurally: **Workers cannot create tasks** (they have 6 tools, none of which is `kanban_add_task`). Only Orchestrators can create tasks, and only Workers can complete tasks. This tool-surface separation makes it architecturally impossible for a Worker to lie about creating sub-tasks — no runtime DB verification needed.

Combined with the existing **CompletionVerifier** (Shell + Semantic dual-layer quality gate) and **DAG dependencies via TaskEdge** (downstream promotion never parses summary prose), Myrm provides stronger anti-hallucination guarantees through architecture rather than runtime patches.

**View on board** opens a filtered Kanban view scoped by `source_chat_id`. Subtasks from Pipeline/Decompose inherit the originating chat’s `source_chat_id`.

### Task Result Editing

Completed, failed, or cancelled tasks can have their `result` and `metadata` fields edited directly from the task drawer in the frontend.

- Click a task card → open the drawer → edit the result inline
- Only available for terminal-state tasks (completed/failed/cancelled) to prevent interference with running tasks
- Each edit emits an `EDITED` event with a payload listing changed fields, providing a full audit trail in the activity feed
- Metadata merges additively — existing keys are preserved unless explicitly overwritten

### Event Timeline & Execution History

The task drawer includes a full **Event Timeline** and **Run History** panel for task-level traceability:

- **Run History**: Each execution attempt shows outcome (success/failure/cancelled), duration, worker ID, and an agent-generated summary. Failed runs include the error message.
- **Event Timeline**: Time-sorted stream of task lifecycle events with color-coded badges — user comments, heartbeat notes, branch switches, verification failures, timeouts, and more. Each event shows its timestamp and payload details.
- **Diagnostics**: Health rules (dead dependencies, long-running, stale tasks) are evaluated and displayed as severity badges on task cards.

### Pipeline Wizard

For complex workflows, use the **Pipeline Wizard** to create a task DAG from a template:

2. Select a template (7 built-in: code review, data analysis, research paper, video production, multi-topic research, content distribution, competitive analysis)

## Sub-Agent Orchestration

When a single agent isn't enough, Myrm's sub-agent system enables multi-agent collaboration with 6 patterns and dynamic discovery capabilities.

### Dynamic Agent Discovery & @ Mention

Myrm supports an intuitive, Coze-like dynamic discovery and delegation mechanism:

- **Dynamic Roster:** Agents with `allow_discovery` enabled are automatically registered into the system's dynamic catalog. The main agent (Planner/Leader) dynamically fetches this roster and learns about its available teammates' capabilities via System Directives.
- **Explicit @ Mention:** In the Chat UI, users can simply type `@` to bring up a ReferenceMentionPopover, autocomplete an agent's name, and explicitly tag them in the message. 
- **Forced Attention:** When an agent is tagged, the backend injects a Forced Attention Directive, guaranteeing the main agent will delegate the task to the tagged sub-agent instead of hallucinating or ignoring the request.
- **Speaker Identity:** The `memory_context_middleware` injects `[Agent: {Name}]` prefixes into AI messages, completely eliminating "split-brain" hallucinations where agents forget who said what.

### Orchestration Patterns

| Pattern | Description | Use Case |
|---------|-------------|----------|
| **Spawn** | Single child agent delegation | Offload a side task without blocking the parent |
| **Chain** | Sequential A → B → C | Multi-step pipelines where order matters |
| **Batch** | Parallel independent tasks | Research across multiple topics simultaneously |
| **DAG** | Directed graph with dependencies | Complex workflows with prerequisites |
| **Verified** | Worker + independent Verifier | Critical tasks requiring cross-validation |
| **Swarm Fission** | Autonomous fission/merge | Exploratory tasks that may spawn sub-tasks dynamically |
| **Alternatives** | N agents produce competing solutions | Generate multiple approaches, user picks the best one |

### Verified Pattern (Adversarial Verification & Zero-Trust)

The Verified pattern prevents agents from "self-grading" or hallucinating success:

1. **Worker** agent executes the task
2. **Workspace Diff Injection**: The system automatically takes a stat-based snapshot of the workspace before and after Worker execution, then injects a human-readable file-change diff into the Verifier's prompt — exposing all modified, added, and removed files regardless of what the Worker reported
3. **Physical Evidence Required**: The worker must return structural `verifiable_credentials` (e.g., file paths, CLI exit codes) instead of just a natural language summary. Claiming PASS without physical evidence is forced to FAIL.
4. **Verifier** agent independently reviews the result, the workspace diff, and the physical evidence in a read-only sandbox
5. If verification fails, the Worker retries with the Verifier's feedback
6. **Real-time Verdict Events**: Each verification round emits a structured `VERIFICATION_VERDICT` SSE event to the frontend, showing PASS/FAIL status, confidence level, and findings summary in the chat progress steps
7. Maximum retry count is configurable

This ensures high-quality output for critical tasks and completely eradicates "hallucinated success".

### Budget Control & Circuit Breakers

Sub-agents operate under strict budget and logic limits:

| Dimension | Description |
|-----------|-------------|
| `max_descendants` | Maximum total sub-agents spawned (default: 20) |
| `max_children_per_agent` | Maximum direct children per agent (default: 5) |
| `max_spawn_depth` | Maximum nesting depth |
| `context_budget` | Independent token budget per sub-agent |
| `budget_tokens` / `max_cost_usd` | Hard spending limits |
| `max_agent_iterations` | **Circuit Breaker:** Physical iteration steps limit to prevent infinite loops |

**Smart Model Downgrade**: When budgets are near exhaustion or certain limits are triggered, Myrm can automatically downgrade the sub-agent from an expensive reasoning model to a cheaper, faster model, preventing budget burn while still attempting to complete the task. Budget exhaustion produces structured errors with clear reasons, not silent failures.

### Agent-to-Agent Communication (ATA)

When multiple agents collaborate on related tasks, they can communicate directly without going through a parent coordinator:

- **`kanban_comment`** — Any worker can leave comments on any task's thread (not just their own), sharing intermediate findings, flagging issues, or coordinating with sibling tasks. Comments support Markdown and are displayed with author identity in the Event Timeline.
- **`TeammateMailbox` P2P** — Session-scoped mailbox with JSONL persistence for direct agent-to-agent messaging. Messages survive process restarts. Built-in rate limiting (30 messages per sender per 60 seconds) prevents agent communication storms.
- **Agent Identity** — Each task card in the Kanban UI displays the assigned agent's name and avatar. The task drawer includes a full agent assignment dropdown with avatar preview, making team composition visible at a glance.
- **Multimodal Context** — Tasks support file attachments via `TaskAttachment`, and the context builder automatically assembles multimodal queries (text + images) for vision-capable models.
- **One-click attachments on the board** — When a worker attaches files, the task card shows a paperclip badge; one click opens the Task Drawer to preview or download—no hidden double-click shortcuts required.

### Workspace Isolation & UI Blacklisting

Each sub-agent runs in an isolated workspace and system sandbox:

- **CoW cloning** — Copy-on-Write workspace duplication
- **Precise sync** — Only modified files are synced back
- **.git protection** — Git directory is excluded from operations
- **Automatic GC** — Three-layer garbage collection (stale events, run records, workspace dirs) runs every 6 hours and on startup. Archived task workspaces are safely deleted with harness-dir boundary checks, and DB paths are nulled to prevent repeated scans — zero manual maintenance required
- **UI Interaction Blacklisting** — Sub-agents running in the background are completely physically blocked from using UI interaction interfaces (like `interactive_feedback` or `send_message`), ensuring they never pop up windows to interrupt the user unexpectedly.

### Line-Level Conflict Detection

When multiple sub-agents work on the same codebase concurrently, Myrm prevents file corruption through line-level conflict detection:

- **Pre-write checking** — Before any file write, the system checks if another agent has recently modified overlapping line ranges in the same file
- **Dual-severity response** — Overlapping line ranges trigger a blocking error (prevents the write), while edits to different regions of the same file produce a non-blocking warning
- **Zero network overhead** — Conflict detection runs entirely within the harness layer, with no control-plane round-trips
- **Automatic cleanup** — When a sub-agent completes, its file activity records are cleared

This approach is strictly more precise than semantic-distance-based collision detection used by some competitors — it operates at exact line ranges rather than approximate semantic proximity.

### Seamless Human-in-the-Loop (HITL)

When an agent hits a checkpoint or needs approval (like `PENDING_APPROVAL`), the user gets a UI popup. 
Beyond simple Accept/Reject, Myrm's HITL supports **Context Injection**: the user can provide explicit text instructions ("Wait, also change the color to red"), and the agent resumes with this injected context seamlessly.

### Non-Fatal Timeout

Most agent frameworks kill sub-agents that exceed their time budget — all progress is lost, and you have to start over.

Myrm takes a fundamentally different approach: **timed-out sub-agents keep running in the background**.

- The parent agent receives a partial result with `still_running: true`, so it can continue with other work immediately
- When the sub-agent finishes, an **event-driven callback** automatically wakes the parent agent — no polling, no manual checks
- The completed result is available for the parent's next turn with semantically clean serialization (no misleading completion timestamps)
- **3 cancellation strategies** (Immediate / Graceful / Checkpoint) give you fine-grained control if you do want to stop a sub-agent

**What this means for you:** Long-running research tasks, code generation, or complex analysis never lose progress to arbitrary timeouts. Your agents work like a real team — if someone takes longer than expected, the team keeps moving and picks up the result when it's ready.

### Delegation Heartbeat & Gateway Keepalive

When a sub-agent runs for minutes (large code refactors, deep research, complex analysis), the parent's SSE connection must stay alive — otherwise proxies, load balancers, or the gateway itself will drop the idle connection and the user sees a mysterious disconnect.

Myrm solves this with **three complementary heartbeat layers**:

1. **Tool-level heartbeat** — Every tool call (including `delegate_task` itself) emits a `TOOL_HEARTBEAT` SSE event every 3 seconds with elapsed time. This keeps the parent stream active while any tool runs.
2. **Event forwarding** — The `SubagentEventForwarder` translates 14 child event types into parent-visible SSE events (progress %, tool logs, status). Each forwarded event naturally refreshes the connection.
3. **Staleness detection** — If no effective progress (token growth or tool completion) occurs within a configurable threshold, a `SUBAGENT_STALE` event fires with diagnostic context (wasted tokens, cost, current tool). In-tool execution uses a relaxed multiplier to avoid false positives during long computations.

Combined with the Gateway's 3-tier timeout strategy (goal mode: 1 hour, fission: 2x default, standard: 5 minutes), delegation never drops — even for sub-agents running 30+ minutes.

**vs. competitors:** Other frameworks (including those claiming "delegation heartbeat" in marketing) lack actual implementation — their long-running sub-tasks silently disconnect, forcing users to retry from scratch.

## Completion Verification

Every task, whether Kanban or conversational, can be verified before being marked complete.

### CompletionVerifier Protocol

```python
class CompletionVerifier(Protocol):
    async def verify(self, task: KanbanTask, result: str) -> VerificationResult: ...
```

Verification results include:
- `passed` — Whether the task meets acceptance criteria
- `reason` — Explanation of the verdict
- `error_logs` — Specific issues found

### Goal-Level Verification

Goals support layered verification with cost-optimized execution order:

1. **Shell verification (zero LLM cost)** — Run objective commands in the sandbox (e.g., `test -f /output.csv`, `curl -sf localhost:8080/health`). Failures short-circuit immediately — no LLM call needed.
2. **Semantic verification (LLM judge)** — Only triggered when all shell criteria pass. An independent LLM assesses the result against acceptance criteria to catch subjective quality issues.

This layered approach eliminates unnecessary LLM costs for objectively verifiable criteria while maintaining semantic depth for quality assessment.

## Task Diagnostics

Myrm includes a built-in diagnostic engine that proactively detects unhealthy tasks and surfaces actionable recommendations.

### 6 Diagnostic Rules

| Rule | Detects | Action |
|------|---------|--------|
| **Stranded in Ready** | Task sitting in READY too long without being picked up | Archive or check dispatcher |
| **Repeated Failures** | High consecutive failure count (auto-blocked) | Review task description or archive |
| **Stuck in Blocked** | Task blocked for too long without resolution | Add comment, unblock, or archive |
| **Dead Dependency** | All parent tasks are in terminal failed/archived state | Archive the orphaned task |
| **Stranded in Triage** | Rough idea sitting in TRIAGE without being specified | Run Specify or archive |
| **Block→Unblock Cycling** | Task repeatedly blocked by agent after being unblocked — root cause not addressed | Review block reasons, try different intervention |

### Severity Auto-Escalation

Each rule automatically escalates severity based on how far past the threshold the task is:

- **Warning** (1×–2× threshold) — yellow badge on card
- **Error** (2×–7× threshold) — orange badge
- **Critical** (≥7× threshold) — red badge with urgent attention needed

### Card-Level Badges

Diagnostic results are evaluated at O(1) cost per card and displayed as severity badges directly on Kanban cards. Click any badge to open the diagnostic drawer with detailed explanations and one-click action buttons (archive, unblock, add comment, etc.).

### Task IM Notifications

When a task completes, fails, or becomes **blocked**, Myrm instantly pushes a notification to all configured IM channels (Feishu / DingTalk / WeCom / Telegram / Slack / Discord, etc.) with the task title and a brief summary.

- **Completed** — success notification with result summary
- **Failed** — failure notification with error context
- **Blocked** — immediate alert with the block reason so you can intervene promptly; scheduled retry blocks (e.g., "retry in 15 minutes") are silently filtered to avoid notification noise

All notification templates support 4 locales (en / zh-CN / zh-TW / ja) and auto-adapt to the user's language preference.
